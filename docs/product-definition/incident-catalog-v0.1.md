# Каталог инцидентов v0.1

**Продукт:** модуль контроля нарушений Set Mark
**Версия:** 0.1
**Статус:** предзаполненный рабочий каталог для проверки Product Manager
**Ревью:** вынесено на внешнее согласование в ветке `review/product-definition-v0.1`
**Связанные артефакты:** [Domain Model v0.1](domain-model-v0.1.md), [Decision Model v0.1](decision-model-v0.1.md), [Нормативный реестр v0.1](regulatory-register-v0.1.md)

## 1. Назначение

Каталог определяет, как известные категории отклонений True API рассматриваются в продукте. Каждая запись отклонения создаёт инцидент, даже если она находится вне области ответственности Set Mark, объясняется допустимым сценарием или пока не поддержана правилом анализа.

Каталог v0.1 является базовой версией для дальнейшего развития. Каноническим источником его кодов и названий на этом этапе являются встроенные справочники документа True API v704.0: «Категории отклонений», «Виды отклонений» и «Результаты выявления отклонений» на страницах 1229–1234. Изменения состава инцидентов, правил анализа и рекомендуемых настроек в процессе создания продукта являются штатным версионируемым развитием каталога. В колонке «Вид отклонения Честного знака» допускаются только названия, дословно подтверждённые справочником `ANALYTICAL_VIOLATIONS_NAMES`, выгрузкой «Отклонения» или официальными материалами «Честного знака». Внутренние аналитические сценарии Set Mark не должны выдаваться пользователю за виды отклонений Честного знака.

## 2. Значения полей

| Поле | Значение |
|---|---|
| Область выбытия | Возникло ли отклонение при розничной реализации/выбытии; все такие отклонения входят в область продукта независимо от контура устранения |
| Контур устранения | Система или процесс, где устраняется первопричина: Set Mark, SetRetail, ГИС МТ или внешний бизнес-процесс; допускается несколько контуров |
| Инцидент | Всегда «Да» для полученной записи True API |
| Правило анализа | ID правила Decision Model либо `TBD` |
| Риск автоштрафа | `Да` только по действующему правилу [Нормативного реестра](regulatory-register-v0.1.md) при выполнении всех его условий; во всех остальных случаях — `Нет` |
| Регуляторный риск | Может ли повторяемость типа учитываться как индикатор риска |
| Рекомендуемая настройка | Точный путь, процессинг, параметр и целевое значение в актуальной конфигурации магазина в Set Centrum |
| Статус строки | Степень готовности записи каталога |

Названием инцидента в таблице выше является точное наименование **результата выявления отклонения**. Категория и вид сохраняются как отдельные классификационные поля: их коды нельзя подменять кодом результата.

### 3.2. Общие пути настройки

Все значения анализируются на уровне магазина в Set Centrum.

| Назначение | Путь и целевое состояние |
|---|---|
| Подключение кассы к Set Mark | `Интеграция → Внешние процессинги → Сервисы валидации маркированных товаров → Сервер валидации SetMark Centrum` |
| Передача ошибок в Set Mark | В процессинге `Сервер валидации SetMark Centrum` включить `Сохранять результат проверки сведений о товаре в журнале нарушений` |
| Запрет продажи без ответа Set Mark | В процессинге `Сервер валидации SetMark Centrum` выключить `Разрешать операцию, при недоступности сервера` и, для алкоголя, `Разрешать операцию, при недоступности сервера (Алкоголь)`, если иной режим отдельно не подтверждён |
| Запрет продажи без считывания КМ | В процессинге `Сервер валидации SetMark Centrum` выключить `Продавать маркированный товар по RFID` и `Продавать маркированный товар по артикулу товара`, если такие сценарии отдельно не разрешены |
| Онлайн-проверка ЧЗ | `Интеграция → Внешние процессинги → Сервисы валидации маркированных товаров → Валидация в сервисе Честный знак`; включить применимые товарные группы |
| Продажа при отсутствии ответа ЧЗ | В процессинге `Валидация в сервисе Честный знак` выключить `Разрешить продажу при отсутствии ответа от ЧЗ`, если продажа должна переходить на настроенный ЛМ ЧЗ и нет отдельного разрешённого аварийного сценария |
| Офлайн-проверка ЛМ ЧЗ | `Интеграция → Внешние процессинги → Сервисы валидации маркированных товаров → Локальная валидация марок в Честном знаке`; заполнить подключение и установить `Версия API (1/2) = 2` |
| Категории ЛМ ЧЗ | Отдельно не задаются: используются категории, включённые в онлайн-процессинге `Валидация в сервисе Честный знак` |
| ИНН и токен | В процессинге `Валидация в сервисе Честный знак` проверить `JSON строка ИНН-токен` и соответствие ИНН юридическому лицу, от имени которого регистрируется продажа |

Указанные значения являются рекомендуемой безопасной базой для снижения нарушений. Исключения для товарной группы, версии SetRetail или аварийного режима должны быть подтверждены отдельно и отображаться в анализе, а не скрываться.

## 5. Пороговые критерии регуляторного риска

Проценты из нормативного документа — не допустимая доля нарушений. Это пороги срабатывания индикатора риска, который может стать основанием для контрольного мероприятия. Цель продукта остаётся прежней: сведение количества нарушений к нулю.

Доля рассчитывается для конкретного объекта розничной продажи за календарный месяц относительно среднемесячного объёма реализации соответствующей продукции. Для применения правила необходимо учитывать вид отклонения, товарную группу, факт запроса сведений о запрете продажи, период расчёта и статус нормативного акта.

### 5.1. Продажа без проверки кода маркировки

| Товарная группа | Порог индикатора риска |
|---|---:|
| Биологически активные добавки | Более 200% |
| Парфюмерно-косметическая продукция с антимикробным действием для гигиены рук и кожные антисептики | Более 200% |
| Пиво и отдельные слабоалкогольные напитки | Более 350% |
| Безалкогольные напитки | Более 10% |

### 5.2. Продажа товара с кодом, ранее выведенным из оборота

| Товарная группа | Условие | Порог индикатора риска |
|---|---|---:|
| Биологически активные добавки | Независимо от запроса сведений | Более 5% |
| Парфюмерно-косметическая продукция с антимикробным действием для гигиены рук и кожные антисептики | Продавец запрашивал сведения о запрете продажи | Более 20% |
| Та же товарная группа | Продавец не запрашивал сведения о запрете продажи | Более 10% |
| Безалкогольные напитки | Продавец запрашивал сведения о запрете продажи | Более 1% |
| Безалкогольные напитки | Продавец не запрашивал сведения о запрете продажи | Более 5% |

Значения выше должны храниться как версионируемые регуляторные правила. Перед использованием для автоматической критичности необходимо зафиксировать:

- реквизиты и статус нормативного акта: проект / принят / вступил в силу / утратил силу;
- дату начала и окончания действия;
- точное соответствие вида отклонения Честного знака;
- товарную группу;
- формулу знаменателя и правила округления;
- разрез расчёта — конкретный объект розничной продажи;
- факт запроса сведений о запрете продажи, если он влияет на порог.

## 7. Правила ведения каталога

1. Официальный код и название берутся только из подтверждённого источника True API.
2. Строка получает риск автоштрафа «Да» только при подтверждённом нормативном основании, действовавшем на дату кассовой операции, и выполнении остальных его условий; иначе значение равно «Нет».
3. Изменения законодательства и справочника True API требуют новой версии каталога. Новая версия применяется только к новым инцидентам; ранее созданные инциденты автоматически не пересчитываются.
4. Новый неизвестный тип не отбрасывается и получает `RA-05`.
5. Отклонение, не связанное с розничной реализацией/выбытием, получает `RA-03: Отклонение не относится к поддерживаемым процессам выбытия`, а не удаляется.
6. Внешний контур устранения сам по себе не является основанием для `RA-03`: все отклонения розничной реализации/выбытия анализируются и остаются в области продукта.
7. Для каждого поддерживаемого типа должны быть определены необходимые данные и хотя бы одно правило анализа.
8. Превышение накопленного процентного порога делает критическим агрегированный показатель магазина, а не отдельные инциденты. Инциденты получают признак участия и ссылку на агрегат.
9. Рекомендуемая настройка хранится отдельно от текущей настройки магазина и должна иметь версию.
10. Каталог не должен смешивать тип отклонения и допустимый/недопустимый сценарий операций.
11. При совпадении кода идентификации расхождение времени между Честным знаком и SetRetail не блокирует корреляцию; оно отображается в объяснении.

## 8. Явные ограничения v0.1

- Официальный перечень из True API v704.0 принят источником, но его полное построчное сопоставление с каталогом ещё выполняется.
- Для `INC-001`–`INC-008` подтверждены коды и иерархия «категория → вид → результат» по встроенному справочнику True API v704.0; актуальность состава должна проверяться по `ANALYTICAL_VIOLATIONS_NAMES`.
- Для `INC-007` подтверждён код, но ещё требуется определить бизнес-смысл статуса РД и границу ответственности Set Mark.
- `INC-009` является служебным типом Set Mark и не должен отображаться как название отклонения Честного знака.
- Код идентификации из отчёта Честного знака принят как точный ключ корреляции; преобразование форматов между системами должно сохранять его без потери значимых символов.
- Не определены все нормативные основания автоштрафов по датам и товарным группам.
- В каталог перенесены подтверждённые процентные пороги, но для каждого из них ещё требуется зафиксировать статус нормативного акта и дату начала действия.
- Полный перечень процентных порогов из нормативного документа ещё не сопоставлен со всеми видами отклонений каталога.
- Рекомендуемые значения конфигурации являются безопасной базой и ещё требуют проверки по поддерживаемым версиям SetRetail и товарным группам клиента.
- Актуальная настройка Set Centrum не доказывает, что это же значение действовало в момент инцидента или было применено на кассе.
- Каталог рекомендаций намеренно не разрабатывается на этом шаге.

## 11. Критерий готовности версии 1.0 каталога

Каталог готов к версии 1.0, когда:

- перенесён полный официальный перечень отклонений True API;
- по каждой строке подтверждена область ответственности;
- для каждого поддерживаемого типа утверждено правило анализа;
- определены необходимые источники и поля;
- подтверждены нормативные основания критичности;
- все применимые процентные пороги перенесены в версионируемый реестр с реквизитами и сроками действия;
- согласованы рекомендуемые настройки;
- все открытые вопросы либо закрыты, либо явно отложены за пределы v1;
- решения зарегистрированы в Product Compiler и трассируются к требованиям.
