# Получение и импорт отклонений ГИС МТ через True API v0.1

**Функция Set Mark:** контроль нарушений  
**Статус:** проект единой спецификации для ревью Product Manager  
**Применимость:** MVP1  
**Граница документа:** получение и сохранение отклонений ГИС МТ. Корреляция с событиями Set Mark и анализ причин выполняются отдельным процессом.

## 1. Назначение

Set Mark должен получать через True API сведения об отклонениях ГИС МТ для организаций, обслуживаемых Set Mark Centrum, и надёжно сохранять полученный набор данных для последующей обработки.

Результатом интеграции является сохранённый набор отклонений ГИС МТ. Корреляция отклонений с событиями Set Mark, поиск операций по коду маркировки и последующий анализ не входят в контур интеграции True API и выполняются отдельным процессом после завершения импорта.

Ошибка или невозможность последующей корреляции и анализа не должна изменять результат уже успешно выполненного импорта из ГИС МТ.

## 3. Граница ответственности

### Входит в интеграцию True API

- выбор организации/ИНН;
- авторизация пользователя через УКЭП и получение токена True API;
- определение товарных групп организации;
- расчёт периода синхронизации;
- создание заданий `VIOLATIONS`;
- ожидание готовности заданий;
- получение идентификаторов результирующих выгрузок;
- скачивание ZIP и всех частей результата;
- чтение CSV;
- дедупликация по номеру отклонения;
- сохранение новых отклонений;
- сохранение поля `Нивелировано` как части исходных данных без специальной бизнес-обработки в MVP1;
- сохранение неизвестных текущей версии Set Mark отклонений без потери данных;
- контроль полноты, ошибок и успешности запуска.

### Не входит в интеграцию True API

- поиск событий Set Mark по коду маркировки;
- сопоставление отклонения с продажами, возвратами, отменами и проверками;
- определение магазина/кассы по внутренним данным;
- создание диагностического контекста;
- анализ причины и формирование RA-01–RA-05.

Эти действия являются следующим независимым этапом обработки.

## 4. Контур организации и состояние синхронизации

Set Mark Centrum может обслуживать несколько ИНН. Каждый ИНН имеет независимый контур авторизации и синхронизации. Ошибка получения данных для одного ИНН не должна блокировать получение данных для другого.

Для каждого ИНН отдельно хранится как минимум:

- дата/время последней попытки (`lastAttemptAt`);
- дата/время последней полностью успешной синхронизации (`lastSuccessfulSyncAt`);
- период последнего запуска;
- идентификаторы заданий и результатов True API;
- пользователь-инициатор и технические сведения об использованном сертификате без закрытого ключа;
- последняя ошибка;
- счётчики полученных, новых, повторных и ошибочных записей.

Параллельный второй SyncRun для одного ИНН в MVP1 не запускается. Синхронизации разных ИНН независимы.

## 5. Запуск и авторизация MVP1

В MVP1 получение отклонений запускается вручную пользователем кнопкой в Set Mark, потому что для получения токена требуется доступная пользователю УКЭП.

Пользователь:

1. выбирает ИНН;
2. выбирает доступную на своём компьютере УКЭП;
3. подписывает данные, необходимые True API для авторизации;
4. Set Mark передаёт подпись и получает токен;
5. последующие технические запросы выполняются с полученным токеном без повторной подписи, пока токен действителен.

Согласованное правило: токен действует 8 часов и может использоваться для всех запросов выбранного ИНН в рамках этого срока. Требование доменной модели о действующей МЧД сохраняется, если она необходима для выполнения операций от имени организации.

Если токен истёк до завершения SyncRun, процесс переходит в состояние `AUTH_REQUIRED`; пользователь повторно авторизуется УКЭП, после чего Set Mark повторяет незавершённый технический запрос и продолжает существующий SyncRun. Уже импортированные записи не импортируются повторно благодаря дедупликации.

### 5.1. Целевой периодический режим

Архитектура не должна исключать будущий автоматический периодический запуск. Для него потребуется постоянный доступ Set Mark к допустимому средству подписи/авторизации без участия пользователя.

Получение такой постоянно доступной подписи не входит в задачи MVP1 и не должно блокировать разработку интеграции с использованием УКЭП сотрудника.

Ограничение True API в 5 выгрузок `VIOLATIONS` в сутки на одну товарную группу сохраняется и должно учитываться как в ручном, так и в будущем автоматическом режиме.

## 6. Период синхронизации

### 6.1. Первый успешный запуск

При отсутствии `lastSuccessfulSyncAt` Set Mark запрашивает последние **90 календарных дней, включая текущий день**.

Это продуктовое значение укладывается в ограничение True API: один `VIOLATIONS`-запрос может содержать до 91 дня включительно.

### 6.2. Последующие запуски

Начало следующего периода — календарная дата последней полностью успешной синхронизации, а не её точное время.

Пример:

```text
lastSuccessfulSyncAt = 2026-09-01 15:00
следующий запуск     = 2026-09-08

dataStartDate = 2026-09-01
dataEndDate   = 2026-09-08
```

Таким образом весь день предыдущей успешной синхронизации запрашивается повторно. Это защищает от неполного результата за текущий день: отклонение за утреннюю операцию может появиться в ГИС МТ позднее в тот же день.

Частота запуска пользователем не влияет на алгоритм периода: данные могут запрашиваться ежедневно, раз в несколько дней или раз в неделю.

Если интервал от `lastSuccessfulSyncAt` до текущей даты превышает допустимый True API диапазон, Set Mark должен разбить его на последовательные окна не более 90 календарных дней.

Для MVP1 не предполагается постоянное перечитывание уже закрытых старых периодов. После того как календарная дата вошла в полностью успешную синхронизацию и последующая синхронизация началась с этой даты, более ранние даты повторно не запрашиваются.

## 7. Определение товарных групп

В контракте `VIOLATIONS` параметр `productGroupCode` обязателен. Поэтому одна логическая синхронизация ИНН состоит из отдельных заданий по товарным группам.

Set Mark должен:

1. получить через `/participants` товарные группы, подключённые к выбранному ИНН;
2. оставить группы, для которых в текущем True API доступна выгрузка `VIOLATIONS`;
3. проверить доступное число выгрузок по товарным группам через метод `available_count`;
4. создать отдельное задание `VIOLATIONS` для каждой допустимой группы.

Пользователь не выбирает товарные группы вручную.

Внешнее ограничение: не более 5 выгрузок `VIOLATIONS` в сутки на одну товарную группу. Это ограничение относится к созданию выгрузок по ТГ, а не к общему числу технических REST-вызовов статуса/скачивания.

## 8. Создание задания VIOLATIONS

Для каждой товарной группы создаётся однократное задание с параметрами:

```json
{
  "name": "VIOLATIONS",
  "dataStartDate": "yyyy-MM-dd",
  "dataEndDate": "yyyy-MM-dd",
  "format": "CSV",
  "periodicity": "SINGLE",
  "params": "{...}",
  "productGroupCode": 2
}
```

`params` передаётся как JSON-строка. Цель Set Mark — получить все отклонения выбранной товарной группы за период, поэтому бизнес-фильтры по GTIN, категории, виду, результату или операции не применяются, если контракт True API допускает их отсутствие.

Если конкретная версия/стенд True API требует явно заполненные значения фильтров, Set Mark должен сформировать эквивалент запроса «все доступные значения» без исключения отклонений из-за бизнес-логики Set Mark.

## 9. Асинхронный workflow

Один пользовательский запуск для одного ИНН создаёт один логический `SyncRun`:

```text
SyncRun(INN, period)
  ├─ ProductGroup A → taskId
  ├─ ProductGroup B → taskId
  └─ ProductGroup N → taskId
```

После создания заданий дальнейшая обработка выполняется без присутствия пользователя, пока токен действителен:

```text
AUTH
 → create VIOLATIONS tasks (8.3.15.1)
 → wait/check task status (8.5)
 → obtain resultId / resultFileParts (8.6)
 → download ZIP(s) (8.7)
 → parse CSV
 → persist deviations
```

Статусы задания True API должны обрабатываться согласно PDF True API. Завершённая выгрузка считается готовой к получению результата только в соответствующем успешном конечном статусе; ошибочные/отменённые/архивные задания считаются незавершёнными для целей SyncRun.

Результат может состоять из основного файла и нескольких частей. Конкретная товарная группа считается полностью полученной только после успешного скачивания и обработки всех частей результата.

## 10. Статусы SyncRun

Рекомендуемая модель MVP1:

```text
CREATED
AUTH_REQUIRED
EXPORT_REQUESTED
WAITING_EXPORTS
DOWNLOADING
IMPORTING
SUCCESS
PARTIAL_FAILED
FAILED
```

Для отдельной товарной группы допускается техническая детализация:

```text
PENDING
TASK_CREATED
PREPARATION
COMPLETED
DOWNLOADED
IMPORTED
FAILED
```

Пользовательский интерфейс может отображать упрощённые русские наименования, технический статус сохраняется для диагностики.

## 11. Критерий успешности и частичные ошибки

`lastSuccessfulSyncAt` обновляется **только после полного успешного импорта всех товарных групп и всех файлов/частей**, включённых в SyncRun.

Успешно импортированные данные при частичной ошибке не откатываются.

Пример:

```text
ТГ A → IMPORTED
ТГ B → IMPORTED
ТГ C → FAILED

SyncRun → PARTIAL_FAILED
lastSuccessfulSyncAt → не изменяется
```

Следующий запуск снова рассчитывается от предыдущего `lastSuccessfulSyncAt`. Повторно пришедшие UUID распознаются как уже известные.

## 12. Повторные попытки

- `401` / истёкший токен: новая авторизация пользователя через УКЭП, затем повтор незавершённого запроса;
- timeout / временная сеть / `5xx`: ограниченные автоматические повторные попытки без повторной подписи, пока токен действителен;
- `429`: повтор с соблюдением лимитов True API;
- ошибочный/отменённый/архивный статус задания: новое задание для той же товарной группы и периода, если это допускают текущие лимиты;
- повреждённый ZIP, отсутствующая обязательная структура CSV или нескачанная часть результата: товарная группа не считается успешно импортированной.

## 13. Формат выгрузки и CSV

True API формирует ZIP с CSV. Для выгрузки отклонений используются следующие поля, найденные в документации ЧЗ:

| № | Колонка |
|---:|---|
| 1 | Вид отклонения |
| 2 | Результат проверки |
| 3 | Дата и время регистрации отклонения |
| 4 | Товарная группа |
| 5 | Субъект |
| 6 | Адрес места фиксации отклонения |
| 7 | Номер документа |
| 8 | Код |
| 9 | Идентификатор ВСД |
| 10 | Регистрационный номер ККТ (из чека) |
| 11 | Дата и время выполнения операции, в результате которой было выявлено отклонение |
| 12 | ИНН участника |
| 13 | Номер отклонения |
| 14 | Нивелировано |
| 15 | Объем из ВСД |
| 16 | Единицы измерения из ВСД |
| 17 | Объем из ГИС МТ |
| 18 | Единицы измерения из ГИС МТ |
| 19 | Разницы между объемами |
| 20 | Единицы измерения разницы |
| 21 | % превышения |
| 22 | GTIN |
| 23 | Идентификатор ФИАС |
| 24 | Муниципальный округ |
| 25 | Фискальный номер накопителя из чека операции |
| 26 | Проверка РР |
| 27 | Объём вывода из оборота |
| 28 | Этап расширения |

CSV должен разбираться по названиям колонок, а не по их порядковому номеру. Неизвестные новой версии True API колонки не должны приводить к потере записи: они сохраняются в raw/extras.

## 14. Идентификатор и дедупликация

Внешним уникальным идентификатором отклонения в MVP1 считается поле **`Номер отклонения`**. Оно имеет формат UUID; продуктово считаем, что этот UUID гарантированно уникален для отклонения.

Для уникального ключа **не используются** дата выявления, дата операции, КМ, ККТ или другие атрибуты.

Алгоритм импорта:

```text
Номер отклонения не найден → NEW → сохранить отклонение
Номер отклонения найден     → EXISTING → новый объект не создавать
```

ИНН запроса и ИНН участника сохраняются как отдельные атрибуты для трассировки и контроля корректности данных.

Исходная запись, впервые полученная для UUID, сохраняется как неизменяемый raw snapshot.

В MVP1 ранее импортированное отклонение считается неизменяемым. Повторное получение того же UUID не приводит к обновлению его бизнес-данных и не запускает повторную обработку.

## 15. Нивелированные отклонения

Set Mark получает и сохраняет отклонения независимо от значения поля `Нивелировано`. Нивелированные записи не фильтруются и не считаются мусорными по умолчанию.

На текущем этапе **не фиксируется модель изменения отклонения из ненивелированного в нивелированное или обратно**. До однозначного понимания семантики этого статуса и поведения ГИС МТ поле `Нивелировано` хранится как часть исходного snapshot отклонения.

MVP1 не перечитывает и не изменяет ранее импортированный объект специально ради отслеживания изменения `Нивелировано` и не запускает повторный анализ из-за возможного изменения этого поля.

После накопления реальных данных требования по жизненному циклу нивелирования должны быть уточнены отдельно.

## 16. Неизвестные и неподдерживаемые отклонения

Успешность импорта не зависит от того, умеет ли текущая версия Set Mark анализировать вид отклонения.

Если категория, вид, результат или иное значение неизвестны Set Mark:

- исходная строка должна быть сохранена полностью;
- известные поля должны быть сохранены в нормализованной форме;
- неизвестный код не должен приводить к ошибке всего SyncRun;
- запись должна оставаться доступной для последующего ручного разбора.

Таким образом интеграция выполняет raw-first ingestion: сначала сохраняется факт ГИС МТ, а поддержка его автоматического анализа определяется отдельным downstream-процессом.

## 17. Минимальная техническая телеметрия

Для SyncRun и его задач должны быть доступны:

- ИНН;
- инициатор;
- время начала/завершения;
- запрошенный период;
- набор товарных групп;
- `taskId`, `resultId`, идентификаторы частей;
- статусы True API;
- сообщения об ошибках, если получены;
- число строк CSV;
- число новых и повторных UUID;
- число ошибок импорта;
- итоговый статус запуска.

Закрытый ключ УКЭП не сохраняется.

## 18. Приёмочные сценарии MVP1

1. Первый запуск для ИНН без истории запрашивает 90 календарных дней, получает все доступные ТГ и сохраняет отклонения.
2. Повторный запуск после запроса 01.09.2026 в 15:00 начинает период с `2026-09-01`, а не с 15:00.
3. Повторный `Номер отклонения` не создаёт вторую запись отклонения и не запускает повторную обработку.
4. Неизвестный Set Mark вид отклонения сохраняется и не ломает SyncRun.
5. Отклонение с `Нивелировано = Да` сохраняется без фильтрации; специальный жизненный цикл этого признака в MVP1 не реализуется.
6. Ошибка одной товарной группы оставляет уже импортированные данные других групп, но не обновляет `lastSuccessfulSyncAt`.
7. После истечения токена пользователь получает новый токен УКЭП, и SyncRun продолжается без повторного импорта уже сохранённых UUID.
8. Результат с несколькими частями считается завершённым только после обработки всех частей.

## 20. Связь с будущей корреляцией Set Mark

Пользовательский интерфейс может группировать и показывать данные начиная с полного кода маркировки, потому что это естественный пользовательский разрез товара.

При этом одна марка может иметь несколько разных отклонений. Поэтому:

- **уникальный ключ отклонения** — `Номер отклонения`;
- **полный КМ (`Код`)** — основной ключ для поиска связанных событий Set Mark на следующем этапе;
- дата/время выявления и дата/время операции остаются атрибутами отклонения и контекстом расследования, но не входят в уникальный ключ.

Следующий отдельный документ должен описать процесс:

```text
сохранённое отклонение
 → взять полный Код маркировки
 → найти все доступные события Set Mark по этой марке
 → сформировать историю событий
 → выполнить анализ
```

## 21. Как положить спецификацию в baseline репозитория

После содержательного ревью этого документа необходимо выполнить штатный Product Compiler workflow:

1. зарегистрировать дополнительные source evidence из `True API v704.0.pdf` для авторизации, `8.3.15.1`, методов 8.5–8.7, формата и ограничений;
2. зарегистрировать продуктовые решения этой проработки как `PM-DEC-*` в соответствующих областях;
3. обновить `requirements/05-integrations/integrations.md` и `data-requirements.md`;
4. сохранить целевой `REQ-DEC-018` про 24 часа, но отдельно описать эксплуатационную предпосылку MVP1: пользователь должен запускать получение данных с достаточной частотой; будущая автоматизация требует 24/7-доступа к подписи;
5. в следующем отдельном документе уточнить `REQ-DATA-002`/`REQ-BO-001` по корреляции событий Set Mark;
6. выполнить `python tools/sync_workspace.py --strict-json` и `python tools/validate_workspace.py`;
7. после успешной проверки зафиксировать новый requirements baseline через `tools/commit_requirements.py`.
