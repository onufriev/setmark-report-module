# Получение и импорт отклонений ГИС МТ через True API v0.1

**Функция Set Mark:** контроль нарушений  
**Статус:** проект единой спецификации для ревью Product Manager  
**Применимость:** MVP1  
**Граница документа:** получение и сохранение отклонений ГИС МТ. Корреляция с событиями Set Mark и анализ причин выполняются отдельным процессом.

## 1. Назначение

Set Mark должен получать через True API сведения об отклонениях ГИС МТ для организаций, обслуживаемых Set Mark Centrum, и надёжно сохранять полученный набор данных для последующей обработки.

Результатом интеграции является сохранённый набор отклонений ГИС МТ. Корреляция отклонений с событиями Set Mark, поиск операций по коду маркировки и последующий анализ не входят в контур интеграции True API и выполняются отдельным процессом после завершения импорта.

Ошибка или невозможность последующей корреляции и анализа не должна изменять результат уже успешно выполненного импорта из ГИС МТ.

## 2. Источники и приоритеты

Спецификация сверена с:

- `requirements/05-integrations/integrations.md` — новая интеграция Set Mark с True API и сохранение отклонений;
- `requirements/05-integrations/data-requirements.md` — данные отклонений, справочники, свежесть и объём;
- `requirements/02-system/entities-and-data.md` — одна запись отклонения создаёт один инцидент, исходные данные сохраняются как снимок;
- `docs/product-definition/domain-model-v0.1.md` — контур организации, УКЭП/МЧД и последующая корреляция по коду идентификации;
- `sources/snapshots/true-api-v704-pages-1229-1234.txt` — зарегистрированный снимок справочников категорий, видов и результатов отклонений True API v704.0;
- актуальная официальная инструкция ЦРПТ «Инструкция по формированию выгрузок данных через True API» — контракт выгрузки `VIOLATIONS`, статусы, ограничения, CSV и получение результата;
- актуальная документация True API метода `/participants` — товарные группы, подключённые к участнику;
- решения Product Manager, согласованные при проработке данной интеграции.

> Важно для репозитория: текущий зарегистрированный `SRC-006` подтверждает справочники отклонений, но не весь контракт асинхронной выгрузки. Перед переносом новых пунктов в baseline требований актуальную инструкцию ЦРПТ необходимо зарегистрировать штатным механизмом Product Compiler как отдельный источник/снимок и создать `SRC-EV-*`; продуктовые решения из этой спецификации — зарегистрировать как `PM-DEC-*`.

Номер раздела метода в документации не используется как стабильный API-контракт: в существующем `REQ-INT-001` указан `8.3.15.1`, а в актуальной инструкции ЦРПТ тот же сценарий называется `1.3.15.1`. Канонически интеграция ориентируется на задание `VIOLATIONS` и соответствующие endpoint'ы True API.

## 3. Граница ответственности

### Входит в интеграцию True API

- выбор организации/ИНН;
- авторизация пользователя через УКЭП и получение токена True API;
- определение товарных групп организации;
- расчёт периода синхронизации;
- создание заданий `VIOLATIONS`;
- ожидание готовности заданий;
- получение идентификаторов результирующих выгрузок;
- скачивание ZIP и всех частей результата;
- чтение CSV;
- дедупликация по номеру отклонения;
- сохранение новых отклонений;
- сохранение признака `Нивелировано`;
- сохранение неизвестных текущей версии Set Mark отклонений без потери данных;
- контроль полноты, ошибок и успешности запуска.

### Не входит в интеграцию True API

- поиск событий Set Mark по коду маркировки;
- сопоставление отклонения с продажами, возвратами, отменами и проверками;
- определение магазина/кассы по внутренним данным;
- создание диагностического контекста;
- анализ причины и формирование RA-01–RA-05.

Эти действия являются следующим независимым этапом обработки.

## 4. Контур организации и состояние синхронизации

Set Mark Centrum может обслуживать несколько ИНН. Каждый ИНН имеет независимый контур авторизации и синхронизации. Ошибка получения данных для одного ИНН не должна блокировать получение данных для другого.

Для каждого ИНН отдельно хранится как минимум:

- дата/время последней попытки (`lastAttemptAt`);
- дата/время последней полностью успешной синхронизации (`lastSuccessfulSyncAt`);
- период последнего запуска;
- идентификаторы заданий и результатов True API;
- пользователь-инициатор и технические сведения об использованном сертификате без закрытого ключа;
- последняя ошибка;
- счётчики полученных, новых, повторных и ошибочных записей.

Параллельный второй SyncRun для одного ИНН в MVP1 не запускается. Синхронизации разных ИНН независимы.

## 5. Запуск и авторизация MVP1

Получение отклонений в MVP1 запускается вручную пользователем кнопкой в Set Mark.

Пользователь:

1. выбирает ИНН;
2. выбирает доступную на своём компьютере УКЭП;
3. подписывает данные, необходимые True API для авторизации;
4. Set Mark передаёт подпись и получает токен;
5. последующие технические запросы выполняются с полученным токеном без повторной подписи, пока токен действителен.

Согласованное допущение MVP1: токен действует 8 часов и может использоваться для всех запросов выбранного ИНН в рамках этого срока. Требование доменной модели о действующей МЧД сохраняется, если она необходима для выполнения операций от имени организации.

Если токен истёк до завершения SyncRun, процесс переходит в состояние `AUTH_REQUIRED`; пользователь повторно авторизуется УКЭП, после чего Set Mark повторяет незавершённый технический запрос и продолжает существующий SyncRun. Уже импортированные записи не импортируются повторно благодаря дедупликации.

## 6. Период синхронизации

### 6.1. Первый успешный запуск

При отсутствии `lastSuccessfulSyncAt` Set Mark запрашивает последние **90 календарных дней, включая текущий день**.

Это продуктовое значение укладывается в актуальное ограничение True API: один `VIOLATIONS`-запрос может содержать от 1 до 91 дня включительно.

### 6.2. Последующие запуски

Начало следующего периода — календарная дата последней полностью успешной синхронизации, а не её точное время.

Пример:

```text
lastSuccessfulSyncAt = 2026-09-01 15:00
следующий запуск     = 2026-09-08

dataStartDate = 2026-09-01
dataEndDate   = 2026-09-08
```

Таким образом весь день предыдущей успешной синхронизации запрашивается повторно. Это защищает от отклонений, которые были зарегистрированы в ГИС МТ позднее, хотя относятся к операциям того же календарного дня.

Частота запуска пользователем не влияет на алгоритм периода: данные могут запрашиваться, например, раз в неделю.

Если интервал от `lastSuccessfulSyncAt` до текущей даты превышает допустимый True API диапазон, Set Mark должен разбить его на последовательные окна не более 90 календарных дней, сохраняя перекрытие первого календарного дня относительно последней успешной синхронизации.

## 7. Определение товарных групп

В актуальном контракте `VIOLATIONS` параметр `productGroupCode` обязателен. Поэтому одна логическая синхронизация ИНН состоит из отдельных заданий по товарным группам.

Set Mark должен:

1. получить через `/participants` товарные группы, подключённые к выбранному ИНН;
2. оставить группы, для которых в текущем True API доступна выгрузка `VIOLATIONS`;
3. проверить доступное число выгрузок по товарным группам через метод `available_count`;
4. создать отдельное задание `VIOLATIONS` для каждой допустимой группы.

Пользователь не выбирает товарные группы вручную.

Актуальное внешнее ограничение: не более 5 выгрузок `VIOLATIONS` в сутки на одну товарную группу. Это не является глобальным лимитом REST-вызовов интеграции.

## 8. Создание задания VIOLATIONS

Для каждой товарной группы создаётся однократное задание с параметрами:

```json
{
  "name": "VIOLATIONS",
  "dataStartDate": "yyyy-MM-dd",
  "dataEndDate": "yyyy-MM-dd",
  "format": "CSV",
  "periodicity": "SINGLE",
  "params": "{...}",
  "productGroupCode": 2
}
```

`params` обязателен как JSON-строка, но `gtin`, `violationCategory`, `violationKind`, `violationResult` и `operationType` внутри него являются необязательными фильтрами. Цель Set Mark — получить все отклонения выбранной товарной группы за период, поэтому сужающие фильтры не применяются.

Рабочий вариант — пустой объект `{}` в `params`. Если целевой стенд True API не принимает пустой объект, Set Mark формирует полный набор category/kind/result из актуального справочника отклонений и передаёт его без бизнес-фильтрации.

## 9. Асинхронный workflow

Один пользовательский запуск для одного ИНН создаёт один логический `SyncRun`:

```text
SyncRun(INN, period)
  ├─ ProductGroup A → taskId
  ├─ ProductGroup B → taskId
  └─ ProductGroup N → taskId
```

После создания заданий дальнейшая обработка выполняется без присутствия пользователя, пока токен действителен:

```text
AUTH
 → create VIOLATIONS tasks
 → wait/check task status
 → obtain resultId / resultFileParts
 → download ZIP(s)
 → parse CSV
 → persist deviations
```

Статусы True API задания, которые должен учитывать Set Mark:

- `PREPARATION` — формируется;
- `COMPLETED` — готово, можно получать результат;
- `FAILED` — ошибка;
- `CANCELED` — отменено;
- `ARCHIVE` — результат более недоступен, требуется новое задание.

Результат может состоять из основного файла и `resultFileParts[]`. Конкретная товарная группа считается полностью полученной только после успешного скачивания и обработки всех частей результата.

## 10. Статусы SyncRun

Рекомендуемая модель MVP1:

```text
CREATED
AUTH_REQUIRED
EXPORT_REQUESTED
WAITING_EXPORTS
DOWNLOADING
IMPORTING
SUCCESS
PARTIAL_FAILED
FAILED
```

Для отдельной товарной группы допускается техническая детализация:

```text
PENDING
TASK_CREATED
PREPARATION
COMPLETED
DOWNLOADED
IMPORTED
FAILED
```

Пользовательский интерфейс может отображать упрощённые русские наименования, технический статус сохраняется для диагностики.

## 11. Критерий успешности и частичные ошибки

`lastSuccessfulSyncAt` обновляется **только после полного успешного импорта всех товарных групп и всех файлов/частей**, включённых в SyncRun.

Успешно импортированные данные при частичной ошибке не откатываются.

Пример:

```text
ТГ A → IMPORTED
ТГ B → IMPORTED
ТГ C → FAILED

SyncRun → PARTIAL_FAILED
lastSuccessfulSyncAt → не изменяется
```

Следующий запуск снова рассчитывается от предыдущего `lastSuccessfulSyncAt`. Повторно пришедшие UUID распознаются как уже известные.

## 12. Повторные попытки

- `401` / истёкший токен: новая авторизация пользователя через УКЭП, затем повтор незавершённого запроса;
- timeout / временная сеть / `5xx`: ограниченные автоматические повторные попытки без повторной подписи, пока токен действителен;
- `429`: повтор с соблюдением лимитов True API;
- `FAILED`, `CANCELED`, `ARCHIVE`: новое задание для той же товарной группы и периода, если это допускают текущие лимиты;
- повреждённый ZIP, отсутствующая обязательная структура CSV или нескачанная часть результата: товарная группа не считается успешно импортированной.

## 13. Формат выгрузки и CSV

True API формирует ZIP с CSV. Для выгрузки отклонений актуальная инструкция содержит следующие колонки:

| № | Колонка |
|---:|---|
| 1 | Вид отклонения |
| 2 | Результат проверки |
| 3 | Дата и время регистрации отклонения |
| 4 | Товарная группа |
| 5 | Субъект |
| 6 | Адрес места фиксации отклонения |
| 7 | Номер документа |
| 8 | Код |
| 9 | Идентификатор ВСД |
| 10 | Регистрационный номер ККТ (из чека) |
| 11 | Дата и время выполнения операции, в результате которой было выявлено отклонение |
| 12 | ИНН участника |
| 13 | Номер отклонения |
| 14 | Нивелировано |
| 15 | Объем из ВСД |
| 16 | Единицы измерения из ВСД |
| 17 | Объем из ГИС МТ |
| 18 | Единицы измерения из ГИС МТ |
| 19 | Разницы между объемами |
| 20 | Единицы измерения разницы |
| 21 | % превышения |
| 22 | GTIN |
| 23 | Идентификатор ФИАС |
| 24 | Муниципальный округ |
| 25 | Фискальный номер накопителя из чека операции |
| 26 | Проверка РР |
| 27 | Объём вывода из оборота |
| 28 | Этап расширения |

CSV должен разбираться по названиям колонок, а не по их порядковому номеру. Неизвестные новой версии True API колонки не должны приводить к потере записи: они сохраняются в raw/extras.

Сформированная выгрузка отклонений хранится на стороне ЧЗ ограниченное время (в актуальной инструкции — 14 дней), поэтому Set Mark должен скачивать результат в рамках текущего SyncRun, а не использовать True API как долговременное хранилище.

## 14. Идентификатор, дедупликация и неизменяемость

Внешним уникальным идентификатором отклонения в MVP1 считается поле **`Номер отклонения`**. В актуальном примере ЧЗ оно имеет формат UUID. Продуктовое допущение MVP1: UUID гарантированно уникален между отклонениями.

Алгоритм импорта:

```text
UUID не найден → NEW → сохранить отклонение
UUID найден     → EXISTING → новый объект не создавать
```

ИНН запроса и ИНН участника сохраняются независимо от глобальной уникальности UUID для трассировки и контроля корректности данных.

Исходная запись, впервые полученная для UUID, сохраняется как неизменяемый raw snapshot. Это соответствует действующей модели сущностей репозитория.

Другие поля уже импортированного отклонения в MVP1 считаются неизменяемыми и не вызывают повторную обработку.

## 15. Нивелированные отклонения

Set Mark получает и сохраняет отклонения независимо от значения `Нивелировано`. Нивелированные записи не фильтруются и не считаются мусорными по умолчанию.

Допущение MVP1:

- возможен переход `Нивелировано: Нет → Да`;
- обратный переход специально не поддерживается;
- если ранее известный UUID при повторной загрузке впервые пришёл с `Нивелировано = Да`, Set Mark обновляет текущий технический признак нивелирования;
- immutable raw snapshot первого импорта не перезаписывается;
- повторный анализ существующего отклонения из-за такого изменения в MVP1 не запускается.

Более сложная история изменений/нивелирования откладывается до накопления реальных данных и понимания поведения ГИС МТ.

## 16. Неизвестные и неподдерживаемые отклонения

Успешность импорта не зависит от того, умеет ли текущая версия Set Mark анализировать вид отклонения.

Если категория, вид, результат или иное значение неизвестны Set Mark:

- исходная строка должна быть сохранена полностью;
- известные поля должны быть сохранены в нормализованной форме;
- неизвестный код не должен приводить к ошибке всего SyncRun;
- запись должна оставаться доступной для последующего ручного разбора.

Для отображения названий рекомендуется использовать актуальный True API справочник категорий, видов и результатов (`ANALYTICAL_VIOLATIONS_NAMES`) и хранить локальный snapshot справочника. При появлении значения, известного ЧЗ, но ещё не поддержанного правилами Set Mark, оно может классифицироваться как `KNOWN_UNSUPPORTED`; реально отсутствующее в справочнике значение — как `UNKNOWN`.

## 17. Минимальная техническая телеметрия

Для SyncRun и его задач должны быть доступны:

- ИНН;
- инициатор;
- время начала/завершения;
- запрошенный период;
- набор товарных групп;
- `taskId`, `resultId`, идентификаторы частей;
- статусы True API;
- `errorMessage` / `fullErrorMessage`, если получены;
- число строк CSV;
- число новых и повторных UUID;
- число ошибок импорта;
- итоговый статус запуска.

Закрытый ключ УКЭП не сохраняется.

## 18. Приёмочные сценарии MVP1

1. Первый запуск для ИНН без истории запрашивает 90 календарных дней, получает все доступные ТГ и сохраняет отклонения.
2. Повторный запуск после запроса 01.09.2026 в 15:00 начинает период с `2026-09-01`, а не с 15:00.
3. Повторный UUID не создаёт вторую запись/второй объект отклонения.
4. Неизвестный Set Mark вид отклонения сохраняется и не ломает SyncRun.
5. Нивелированное отклонение сохраняется; переход известного UUID `Нет → Да` обновляет только текущий признак.
6. Ошибка одной товарной группы оставляет уже импортированные данные других групп, но не обновляет `lastSuccessfulSyncAt`.
7. После истечения токена пользователь получает новый токен УКЭП, и SyncRun продолжается без повторного импорта уже сохранённых UUID.
8. Результат с несколькими `resultFileParts` считается завершённым только после обработки всех частей.

## 20. Как положить спецификацию в baseline репозитория

После содержательного ревью этого документа необходимо выполнить штатный Product Compiler workflow:

1. зарегистрировать актуальную официальную инструкцию ЦРПТ как source snapshot;
2. зарегистрировать `SRC-EV-*` для механики `VIOLATIONS`, ограничений, статусов, CSV и товарных групп;
3. зарегистрировать продуктовые решения этой проработки как `PM-DEC-*` в соответствующих областях;
4. обновить `requirements/05-integrations/integrations.md` и `data-requirements.md`;
5. отдельно разрешить конфликт SLA `REQ-DEC-018`;
6. в следующем отдельном документе уточнить `REQ-DATA-002`/`REQ-BO-001` по корреляции событий Set Mark;
7. выполнить `python tools/sync_workspace.py --strict-json` и `python tools/validate_workspace.py`;
8. после успешной проверки зафиксировать новый requirements baseline через `tools/commit_requirements.py`.

До выполнения этих действий данный файл является согласованной спецификацией для ревью, но не подменяет evidence/baseline-механизм Product Compiler.
