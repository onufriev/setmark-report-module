# Модель необходимых действий v0.1

**Продукт:** модуль контроля нарушений Set Mark  
**Версия:** 0.1  
**Статус:** согласованное дополнение к Product Definition  
**Связанные артефакты:** [Domain Model v0.1](domain-model-v0.1.md), [Decision Model v0.1](decision-model-v0.1.md), [Каталог инцидентов v0.1](incident-catalog-v0.1.md)

## 1. Назначение

Документ определяет сущность «Необходимое действие», её связь с результатом анализа инцидента и правила объединения одинаковых действий.

Необходимое действие — это автоматически сформулированная продуктом мера, выполнение которой может устранить выявленную причину, снизить вероятность повторения аналогичных отклонений либо предоставить недостающие данные для достоверного анализа.

Необходимое действие не является задачей workflow. В v1 продукт не назначает ответственного, срок, исполнителя, статус выполнения или SLA и не подтверждает фактическое выполнение действия.

## 2. Место в модели продукта

Базовая последовательность:

```text
Отклонение Честного знака
→ Инцидент
→ Автоматический анализ конкретного инцидента
→ Результат анализа и объяснение
→ Автоматическое формирование нуля, одного или нескольких необходимых действий
→ Объединение одинаковых действий для нескольких инцидентов
```

Действие формируется системой только после анализа конкретного инцидента и только по утверждённому правилу анализа. Сам вид отклонения не является достаточным основанием для безусловного назначения одного и того же действия всем инцидентам этого вида.

Пользователь не выбирает, не подтверждает и не изменяет назначенное системой необходимое действие. В v1 пользователь использует действие как результат анализа и может перейти к связанным инцидентам для проверки основания.

## 3. Связи сущностей

- один инцидент может не иметь необходимых действий, если исправление со стороны пользователя не требуется или действие нельзя определить достоверно;
- один инцидент может иметь несколько необходимых действий, если анализ выявил несколько независимых причин или мер;
- одно необходимое действие может быть связано с несколькими инцидентами;
- связь действия с каждым инцидентом хранит индивидуальное основание, применённое правило и факты конкретного инцидента;
- объединение действий не объединяет и не удаляет сами инциденты.

## 4. Минимальные данные необходимого действия

| Поле | Содержание |
|---|---|
| Идентификатор действия | Стабильный внутренний ID экземпляра агрегированного действия |
| Тип действия | Настройка, проверка данных, исправление внешней регистрации, проверка бизнес-процесса, получение недостающих данных или иной утверждённый тип |
| Формулировка | Конкретное действие, понятное пользователю торговой сети |
| Объект воздействия | Организация, магазин, касса, интеграция, товарная группа, внешний контур или иной объект |
| Целевое состояние | Проверяемый ожидаемый результат или рекомендуемое значение, если оно применимо |
| Основание | Правило анализа, которое автоматически сформировало действие |
| Связанные инциденты | Перечень инцидентов, для которых действие сформировано |
| Количество инцидентов | Число связанных инцидентов в текущем доступном периоде |
| Ожидаемый эффект | Какие повторения или риски может снизить выполнение действия |
| Ограничения | Что продукт не может подтвердить по имеющимся данным |

## 5. Правило автоматического формирования

Система формирует необходимое действие, если одновременно выполнены условия:

1. завершён анализ конкретного инцидента;
2. утверждённое правило анализа допускает конкретное действие для установленного результата;
3. доступны факты, необходимые для выбора действия и объекта воздействия;
4. действие имеет однозначную формулировку и, если применимо, целевое состояние;
5. ограничения анализа не делают действие недостоверным.

Если этих условий недостаточно, исправляющее действие не формируется. Система может сформировать только действие по получению или проверке недостающих данных, если такое действие предусмотрено правилом.

Пользовательские настройки или ручной выбор рекомендации не являются источником необходимого действия.

## 6. Правило объединения одинаковых действий

Действия объединяются только при совпадении всех смыслообразующих признаков:

1. типа действия;
2. объекта воздействия и его идентификатора;
3. конкретной формулировки меры;
4. целевого состояния или рекомендуемого значения;
5. применимой версии правила.

Пример: действия включить один и тот же параметр с одним целевым значением для одного магазина объединяются в одно действие со списком связанных инцидентов.

Действия для разных магазинов, разных параметров, разных целевых значений или разных версий правил не объединяются.

Текст объяснения конкретного инцидента не используется как ключ объединения: он остаётся индивидуальным контекстом связи «инцидент → действие».

## 7. Отображение совокупного эффекта

Для агрегированного действия продукт показывает:

- количество связанных инцидентов;
- виды отклонений, к которым относятся связанные инциденты;
- затронутые объекты;
- период, в котором возникли связанные инциденты;
- ожидаемый эффект от выполнения действия;
- возможность перейти к каждому связанному инциденту и увидеть индивидуальное основание.

Количество связанных инцидентов не доказывает единую первопричину. Оно показывает масштаб потенциального эффекта одного и того же действия по действующим правилам анализа.

## 8. Взаимодействие с результатами анализа

| Результат | Возможность сформировать действие |
|---|---|
| `RA-01` | Да, если утверждённое правило определяет применимую меру |
| `RA-02` | Обычно нет; возможно информационное действие только при наличии отдельного основания |
| `RA-03` | Возможно действие вне Set Mark, если оно достоверно определяется и явно обозначено как внешнее |
| `RA-04` | Возможно действие по получению или проверке недостающих данных; исправляющее действие без достаточного основания не назначается |
| `RA-05` | Действие для пользователя по устранению нарушения не назначается; продукт фиксирует необходимость обновления каталога или правил |

Риск автоштрафа и регуляторный риск не определяют действие автоматически. Они могут влиять на приоритет показа, но действие должно иметь собственное основание в правиле анализа.

## 9. Ограничения v1

- действие является автоматически сформированной рекомендацией, а не подтверждением выполнения пользователем;
- текущая конфигурация Set Centrum не доказывает конфигурацию в момент операции;
- продукт не проверяет доставку настройки на кассу;
- продукт не ведёт статус выполнения, сроки, ответственных и контроль исполнения;
- пользователь может перейти от агрегированного действия к связанным инцидентам, но изменение или закрытие инцидентов через действие не выполняется;
- правила формирования действий фиксируются в Decision Model и Каталоге инцидентов и версионируются;
- пользователь не редактирует и не подменяет результат автоматического формирования действия.

## 10. Инварианты

1. Необходимое действие не создаётся до анализа конкретного инцидента.
2. Необходимое действие формируется системой автоматически по утверждённому правилу анализа.
3. Пользователь не выбирает, не подтверждает и не изменяет необходимое действие.
4. Один вид отклонения не обязан всегда приводить к одному и тому же действию.
5. Каждый инцидент сохраняется как самостоятельная запись независимо от объединения действий.
6. Для каждого связанного инцидента сохраняется индивидуальное объяснение назначения действия.
7. Объединение выполняется по смысловым признакам действия и объекту воздействия, а не по похожести текста.
8. Агрегированное действие показывает потенциальный совокупный эффект, но не объявляет общую первопричину доказанной.
9. Действие без утверждённого правила или достаточных фактов не назначается.
10. Изменение версии правила не изменяет автоматически действия, ранее сформированные для уже созданных инцидентов.

## 11. Решение по расхождению

Расхождение «рекомендации задаются вручную или формируются продуктом» закрывается следующим решением Product Manager:

> Необходимое действие автоматически формируется системой по результату алгоритма анализа конкретного инцидента.

Ручное задание, подтверждение или изменение необходимого действия пользователем не входит в v1.
