# Модель необходимых действий v0.1

**Продукт:** модуль контроля нарушений Set Mark  
**Версия:** 0.1  
**Статус:** согласованное дополнение к Product Definition  
**Связанные артефакты:** [Domain Model v0.1](domain-model-v0.1.md), [Decision Model v0.1](decision-model-v0.1.md), [Каталог инцидентов v0.1](incident-catalog-v0.1.md)

## 1. Назначение

Документ определяет сущность «Необходимое действие», её связь с результатом анализа инцидента и правила объединения одинаковых действий.

Необходимое действие — это автоматически сформулированная продуктом мера, выполнение которой может устранить выявленную причину, снизить вероятность повторения аналогичных отклонений либо помочь пользователю проверить возможную причину, если она не определена достоверно.

Необходимое действие не является задачей workflow. В v1 продукт не назначает ответственного, срок, исполнителя, статус выполнения или SLA и не подтверждает фактическое выполнение действия.

## 2. Место в модели продукта

Базовая последовательность:

```text
Отклонение Честного знака
→ Инцидент
→ Автоматический анализ конкретного инцидента
→ Результат анализа и объяснение
→ Установленная причина либо признак «Причина не определена достоверно»
→ Автоматическое формирование нуля, одного или нескольких необходимых действий
→ Объединение одинаковых действий для нескольких инцидентов
```

Для одного инцидента существует одна фактическая причина отклонения. Продукт либо устанавливает её по доступным данным и утверждённому правилу, либо явно сообщает, что причина не определена достоверно.

Действие формируется системой только после анализа конкретного инцидента и только по утверждённому правилу анализа. Сам вид отклонения не является достаточным основанием для безусловного назначения одного и того же действия всем инцидентам этого вида.

Пользователь не выбирает, не подтверждает и не изменяет назначенное системой необходимое действие. В v1 пользователь использует действие как результат анализа и может перейти к связанным инцидентам для проверки основания.

## 3. Связи сущностей

- один инцидент может не иметь необходимых действий, если исправление со стороны пользователя не требуется;
- если причина установлена достоверно, инцидент получает действие, соответствующее этой причине, если такое действие предусмотрено правилом;
- если причина не установлена достоверно, инцидент может получить несколько возможных действий, предусмотренных правилом для проверки или устранения допустимых вариантов причины;
- несколько возможных действий не означают наличие нескольких причин у одного инцидента;
- одно необходимое действие может быть связано с несколькими инцидентами;
- связь действия с каждым инцидентом хранит индивидуальное основание, применённое правило, факты конкретного инцидента и признак достоверности причины;
- объединение действий не объединяет и не удаляет сами инциденты.

## 4. Минимальные данные необходимого действия

| Поле | Содержание |
|---|---|
| Идентификатор действия | Стабильный внутренний ID экземпляра агрегированного действия |
| Тип действия | Настройка, проверка данных, исправление внешней регистрации, проверка бизнес-процесса, получение недостающих данных или иной утверждённый тип |
| Формулировка | Конкретное действие, понятное пользователю торговой сети |
| Объект воздействия | Организация, магазин, касса, интеграция, товарная группа, внешний контур или иной объект |
| Целевое состояние | Проверяемый ожидаемый результат или рекомендуемое значение, если оно применимо |
| Основание | Правило анализа, которое автоматически сформировало действие |
| Версия правила | Версия правила анализа, применённая при формировании действия |
| Статус причины | `Причина установлена` либо `Причина не определена достоверно` |
| Характер действия | `Основное` для установленной причины либо `Возможное` при неопределённой причине |
| Связанные инциденты | Перечень инцидентов, для которых действие сформировано |
| Количество инцидентов | Число связанных инцидентов в текущем доступном периоде |
| Ожидаемый эффект | Какие повторения или риски может снизить выполнение действия |
| Ограничения | Что продукт не может подтвердить по имеющимся данным |

## 5. Правило автоматического формирования

### 5.1. Причина установлена достоверно

Система формирует необходимое действие, если одновременно выполнены условия:

1. завершён анализ конкретного инцидента;
2. утверждённое правило позволяет установить одну причину отклонения;
3. доступны факты, необходимые для выбора действия и объекта воздействия;
4. правило определяет действие для установленной причины;
5. действие имеет однозначную формулировку и, если применимо, целевое состояние.

Такое действие обозначается как основное и объясняется установленной причиной.

### 5.2. Причина не определена достоверно

Если имеющихся данных недостаточно для выбора одной причины, система не объявляет несколько причин и не выбирает одну из них предположительно.

Система:

1. явно устанавливает статус `Причина не определена достоверно`;
2. объясняет, какие данные отсутствуют или почему доступные факты не позволяют выбрать одну причину;
3. формирует одно или несколько возможных действий, только если они прямо предусмотрены правилом анализа для такого случая;
4. обозначает каждое такое действие как возможное, а не как действие по подтверждённой причине;
5. не утверждает, что выполнение любого отдельного действия гарантированно устранит причину отклонения.

Возможные действия могут включать проверку настроек, данных, интеграции или бизнес-процесса. Они не обязаны ограничиваться только сбором недостающих данных, если правило анализа предусматривает безопасные меры для нескольких допустимых вариантов причины.

Пользовательские настройки или ручной выбор рекомендации не являются источником необходимого действия.

## 6. Версионирование и пересчёт

Каждый инцидент анализируется по версии правил, действующей в момент его создания и первичного анализа. Эта версия сохраняется вместе с результатом анализа и сформированными необходимыми действиями.

После изменения Decision Model, Каталога инцидентов или правила формирования действия:

- новые правила применяются только к новым инцидентам;
- ранее созданные инциденты автоматически не пересчитываются;
- ранее сформированные действия автоматически не изменяются и не удаляются;
- существующее действие не присоединяет новые инциденты, если они обработаны по несовместимой версии правила;
- исторический результат остаётся воспроизводимым по сохранённой версии правила.

Повторный анализ существующего инцидента и миграция исторических результатов не входят в v1 и могут быть определены отдельным продуктовым решением в следующей версии.

## 7. Правило объединения одинаковых действий

Действия объединяются только при совпадении всех смыслообразующих признаков:

1. типа действия;
2. объекта воздействия и его идентификатора;
3. конкретной формулировки меры;
4. целевого состояния или рекомендуемого значения;
5. применимой версии правила;
6. характера действия: основное или возможное.

Пример: действия включить один и тот же параметр с одним целевым значением для одного магазина объединяются в одно действие со списком связанных инцидентов.

Действия для разных магазинов, разных параметров, разных целевых значений, разных версий правил или с разным характером не объединяются.

Текст объяснения конкретного инцидента не используется как ключ объединения: он остаётся индивидуальным контекстом связи «инцидент → действие».

## 8. Отображение совокупного эффекта

Для агрегированного действия продукт показывает:

- количество связанных инцидентов;
- виды отклонений, к которым относятся связанные инциденты;
- затронутые объекты;
- период, в котором возникли связанные инциденты;
- характер действия: основное или возможное;
- ожидаемый эффект от выполнения действия;
- возможность перейти к каждому связанному инциденту и увидеть индивидуальное основание.

Количество связанных инцидентов не доказывает единую первопричину. Оно показывает масштаб потенциального эффекта одного и того же действия по действующим правилам анализа.

## 9. Взаимодействие с результатами анализа

| Результат | Возможность сформировать действие |
|---|---|
| `RA-01` | Да: основное действие при установленной причине либо возможные действия, если причина нарушения не определена достоверно |
| `RA-02` | Обычно нет; возможно информационное действие только при наличии отдельного основания |
| `RA-03` | Возможно действие вне Set Mark, если оно достоверно определяется и явно обозначено как внешнее |
| `RA-04` | Возможны действия по получению данных и иные возможные действия, прямо предусмотренные правилом для неопределённой причины |
| `RA-05` | Действие для пользователя по устранению нарушения не назначается; продукт фиксирует необходимость обновления каталога или правил |

Риск автоштрафа и регуляторный риск не определяют действие автоматически. Они могут влиять на приоритет показа, но действие должно иметь собственное основание в правиле анализа.

## 10. Ограничения v1

- действие является автоматически сформированной рекомендацией, а не подтверждением выполнения пользователем;
- при неопределённой причине возможное действие не считается доказательством этой причины;
- текущая конфигурация Set Centrum не доказывает конфигурацию в момент операции;
- продукт не проверяет доставку настройки на кассу;
- продукт не ведёт статус выполнения, сроки, ответственных и контроль исполнения;
- пользователь может перейти от агрегированного действия к связанным инцидентам, но изменение или закрытие инцидентов через действие не выполняется;
- правила формирования действий фиксируются в Decision Model и Каталоге инцидентов и версионируются;
- пользователь не редактирует и не подменяет результат автоматического формирования действия;
- автоматический пересчёт исторических инцидентов и действий после изменения правил не выполняется.

## 11. Инварианты

1. Необходимое действие не создаётся до анализа конкретного инцидента.
2. Для одного инцидента существует одна фактическая причина отклонения.
3. Продукт либо устанавливает одну причину достоверно, либо явно фиксирует, что причина не определена.
4. Несколько возможных действий при неопределённой причине не означают наличие нескольких причин.
5. Необходимое действие формируется системой автоматически по утверждённому правилу анализа.
6. Пользователь не выбирает, не подтверждает и не изменяет необходимое действие.
7. Один вид отклонения не обязан всегда приводить к одному и тому же действию.
8. Каждый инцидент сохраняется как самостоятельная запись независимо от объединения действий.
9. Для каждого связанного инцидента сохраняется индивидуальное объяснение назначения действия.
10. Объединение выполняется по смысловым признакам действия, объекту воздействия и характеру действия, а не по похожести текста.
11. Агрегированное действие показывает потенциальный совокупный эффект, но не объявляет общую первопричину доказанной.
12. Действие без утверждённого правила не назначается.
13. Изменение версии правила не изменяет автоматически действия, ранее сформированные для уже созданных инцидентов.
14. Новая версия правила применяется только к инцидентам, созданным после её вступления в действие.
15. Результат и действия исторического инцидента должны быть воспроизводимы по сохранённой версии правила.

## 12. Решения по расхождению

### 12.1. Источник необходимого действия

> Необходимое действие автоматически формируется системой по результату алгоритма анализа конкретного инцидента.

Ручное задание, подтверждение или изменение необходимого действия пользователем не входит в v1.

### 12.2. Изменение правил анализа

> Изменение правил анализа не приводит к автоматическому пересчёту уже существующих инцидентов и необходимых действий.

Новые правила применяются только к новым инцидентам. Исторические результаты сохраняются вместе с версией применённого правила.

### 12.3. Причина и действия при неопределённости

> У одного инцидента не может быть несколько фактических причин. Продукт либо устанавливает одну причину, либо сообщает, что причина не определена достоверно.

Если причина не определена, система может сформировать несколько возможных действий, предусмотренных правилом анализа. Эти действия показываются как меры для проверки или устранения возможных вариантов причины и не выдаются за действия по подтверждённой причине.
