# Контрольный отчёт: PRODUCT_DEFINITION

**Продукт:** модуль отчёта по нарушениям Set Mark  
**Редакция:** R3  
**Статус:** Готово к проверке Product Manager  
**Дата:** 2026-07-28

## Суть этапа

Определён MVP функции централизованного мониторинга нарушений маркировки внутри Set Mark. Зафиксированы цели и границы, пользователи и права, модель объектов и инцидентов, правила анализа `RA-01–RA-05`, интерфейсные сценарии, интеграции, данные, качество, исключительные и эксплуатационные сценарии, критерии приёмки и трассировка.

Функция помогает ответственным сотрудникам в первую очередь находить критические инциденты с риском выставления автоштрафа, понимать причину каждого результата анализа и определять дальнейшие действия. Назначение ответственных, постановка задач и контроль устранения не входят в MVP.

## Исправление относительно R2

`PRODUCT_DEFINITION-R2` не утверждён и переведён в статус устаревшей редакции после последнего замечания Product Manager. В R3 однозначно зафиксирована фактическая и целевая схема интеграций:

1. Сейчас напрямую с Честным знаком взаимодействует только кассовое ПО.
2. Интеграции Set Mark с Честным знаком не существует.
3. Для нового модуля отдельно разрабатывается новая интеграция Set Mark с предоставленным API Честного знака для получения отклонений.
4. Полученные через новую интеграцию отклонения сохраняются в Set Mark и используются модулем для создания и анализа инцидентов.

Ошибочная формулировка `PM-DEC-029` заменена в актуальных требованиях решением `PM-DEC-032`. Историческая запись сохранена только для аудита и не является действующим требованием.

## Ранее внесённые уточнения

- При открытии обзора основное внимание пользователя сразу направляется на визуально выделенные критические инциденты, для которых установлен риск выставления автоштрафа.
- Онлайн Честный знак возвращает кассовому ПО исходные данные и признаки о коде маркировки, а не готовое решение «продавать / не продавать».
- Кассовое ПО применяет действующие правила и формирует собственное решение о допустимости продажи.
- В инциденте раздельно показываются исходные признаки Честного знака, режим проверки, применённая версия правил, решение кассового ПО и фактическое действие кассы.
- Формулировки «Честный знак разрешил продажу» и «Честный знак запретил продажу» не используются для описания онлайн-ответа.

## Пользователи и основные сценарии

- Аналитик по работе с маркировкой открывает обзор сети и сразу видит критические инциденты с установленным риском выставления автоштрафа и связанные с ними объекты.
- Критические инциденты с риском автоштрафа визуально выделяются и выводятся приоритетно; остальные риски и накопления остаются доступны для последующего анализа.
- Пользователь переходит от сети, магазина, кассы, товарной группы или вида нарушения к отфильтрованному списку инцидентов.
- В карточке инцидента доступны исходные данные, результат `RA-01–RA-05`, объяснение, критичность, риск, Контур устранения и рекомендация.
- Карточка не смешивает исходные признаки Честного знака, решение кассового ПО и фактическое действие кассы.
- Выбранный контекст сохраняется при возврате к списку и аналитике; текущую выборку можно выгрузить в CSV.
- Настроенные получатели получают ежедневные уведомления о критичных нарушениях.
- Администратор управляет подключением функции, получателями уведомлений и сроком хранения данных.

## Границы MVP

- Функция поставляется как часть Set Mark и использует его аутентификацию, права, обновление, восстановление и эксплуатационные механизмы.
- Получение отклонений через API Честного знака является новой необходимой интеграционной разработкой в составе решения.
- Один внешний факт отклонения создаёт один инцидент; повторная доставка не создаёт дубликат.
- Сбои функции не влияют на продажи и проверку кодов.
- Неполные, устаревшие и неизвестные данные показываются с явными ограничениями и обрабатываются по утверждённым правилам.
- Управление задачами, назначение ответственных и контроль фактического устранения находятся вне MVP.

## Данные и интеграции

- Кассовое ПО напрямую взаимодействует с онлайн Честным знаком и ЛМ ЧЗ.
- Данные о выполненных кассовым ПО проверках передаются в Set Mark существующими механизмами обмена с кассой и используются как контекст анализа.
- Для нового модуля разрабатывается новая интеграция Set Mark с API Честного знака, включая метод True API 8.3.15.1 «Выгрузка сведений об отклонениях».
- Для анализа используются отклонения, кассовые операции, исходные данные онлайн- и офлайн-проверок, решение кассового ПО, фактическое действие кассы и настройки.
- Исходный снимок события сохраняется; время операции и регистрации нормализуется с сохранением исходных значений.
- Источник рабочего прототипа определён решением `PM-DEC-028`: воспроизводимый набор синтетических файлов на основе структуры предоставленного отчёта Честного знака.
- Клиентский Excel используется только как локальный образец структуры, не сохраняется в репозитории и не переносится в демонстрационный набор.
- Все идентификаторы генерируются заново, распределения балансируются для демонстрации, а seed/reset-скрипты и автоматическая проверка должны подтверждать связи, покрытие `RA-01–RA-05` и отсутствие реальных клиентских идентификаторов.

## Критерии качества и приёмки

- Основные экраны открываются не более чем за 3 секунды для 95% запросов.
- Инцидент появляется не позднее 24 часов после доступности исходных данных.
- Обзор показывает период, свежесть и полноту данных, а критические инциденты с риском автоштрафа доступны без предварительной настройки фильтров.
- Аналитика, фильтры, пороги, CSV и уведомления используют согласованные данные.
- После сбоя обработка автоматически продолжается без потери исходных событий.
- Пользователь на демонстрационных данных без дополнительных объяснений может найти приоритетный объект, открыть инцидент, понять результат и рекомендацию, корректно интерпретировать ограничения данных и выгрузить выборку.
- Объяснение инцидента позволяет определить, связана ли проблема с исходными данными, их получением, применением правил кассовым ПО или фактическим действием кассы.

## Трассировка

Требования связаны с семью проверяемыми частями решения: обзором сети, списком инцидентов и фильтрами, карточкой инцидента, аналитикой и CSV, ежедневными уведомлениями, настройками функции, исключительными и эксплуатационными сценариями.

Ключевые уточнения трассируются следующим образом:

| Изменение | Требования | Решение |
|---|---|---|
| Фактическая и целевая схема взаимодействия с Честным знаком | `REQ-DEC-032`, `REQ-INT-001`, `REQ-INT-003` | `PM-DEC-032` |
| Приоритет критических инцидентов с риском автоштрафа | `REQ-DEC-030` | `PM-DEC-030` |
| Разделение данных Честного знака и решения кассового ПО | `REQ-DEC-031`, `REQ-DEC-007` | `PM-DEC-031` |

Для сценариев, экранов и критериев проверки используются канонические `REQ-*`; каждое требование MVP имеет подтверждённое основание `SRC-EV-*` или `PM-DEC-*`.

## Ограничения следующих этапов

- Визуальный прототип ещё не создан и требует отдельного утверждения этого отчёта.
- Визуальный этап использует подготовленные демонстрационные данные без реальных интеграций и backend.
- Визуальный прототип обязан отражать приоритет критических инцидентов с риском автоштрафа и разделение исходных данных Честного знака, решения кассового ПО и фактического действия кассы.
- Технический паспорт источника данных рабочего прототипа будет заполнен штатным инструментом на этапе `WORKING_PROTOTYPE`, когда появятся точные пути, форматы и команды наполнения и сброса.
- Технологический стек рабочего прототипа должен быть подтверждён отдельно перед его реализацией.
- Решение `PM-DEC-028` не разрешает сохранять клиентский отчёт или реальные клиентские идентификаторы в репозитории.
- Новая интеграция Set Mark с API Честного знака не создаётся на визуальном этапе; её разработка входит в реализацию решения после согласования архитектуры.
