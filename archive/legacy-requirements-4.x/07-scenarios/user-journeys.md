## REQ-DEC-176. Решение Product Manager

**Область:** mainJourney
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-191
**Применимость:** Следующий этап

Переход из ежедневного email-дайджеста открывает список Инцидентов за предыдущий календарный день с фильтром новых критичных отклонений и контекстом организации. Количество записей в открытой выборке соответствует числу в дайджесте; пользователь может продолжить фильтрацию и открыть карточку инцидента.

### Проверка
Реализация соответствует решению PM-DEC-191.
## REQ-DEC-134. Решение Product Manager

**Область:** mainJourney
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-149
**Применимость:** MVP1

В MVP пользователь открывает Обзор, изучает основные агрегаты и распределение отклонений, переходит в Инциденты, применяет поиск, фильтры и группировки и открывает карточку с данными источников. Пользователь также может настроить True API, критичность видов отклонений и вручную запустить синхронизацию. ## REQ-DEC-042. Решение Product Manager

**Область:** mainJourney
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-043, PM-DEC-149
**Применимость:** Следующий этап

Вместо одного линейного пользовательского пути для аналитика зафиксированы два основных пути. Структура путей уточнена Product Manager 27.08.2026.

### Путь 1. Критический контроль

1. Пользователь входит в Set Mark через существующий механизм аутентификации и открывает раздел мониторинга нарушений маркировки.
2. Выбирает период либо использует период по умолчанию «Неделя».
3. Сразу проверяет, есть ли критические инциденты, для которых возможен автоматический штраф.
4. Если критические инциденты есть, пользователь рассматривает их в первую очередь и изучает необходимые действия, предотвращающие повторение таких инцидентов.
5. При необходимости пользователь переходит к связанным инцидентам и карточке инцидента, чтобы понять исходные факты, причину, результат проверки, критичность, Контур устранения и рекомендацию.
6. После определения необходимого действия пользователь переходит к внесению изменений в соответствующем Контуре устранения. Выполнение изменения и контроль результата происходят вне функции.

### Путь 2. Регулярное снижение количества нарушений

1. Если критических инцидентов нет, пользователь оценивает необходимые действия для снижения общего количества нарушений.
2. Пользователь выбирает в первую очередь действия, с которыми связано наибольшее количество инцидентов, чтобы получить максимальный эффект от внесённых изменений.
3. При необходимости переходит от действия к связанным инцидентам, уточняет причины поиском, фильтрами, карточками и аналитикой.
4. Цель регулярного пути — уменьшать количество нарушений и связанный с ними регуляторный риск, в том числе риск последующих проверок и штрафов через индикаторы риска «Честного знака».
5. После выбора действия пользователь вносит изменения в соответствующем Контуре устранения вне функции.

В обоих путях пользователь может использовать кликабельные агрегаты Дашборда, список инцидентов, карточку, аналитику, CSV и PDF как средства детализации и подтверждения принятого решения. Переход из любого агрегата должен открывать ровно соответствующую выборку инцидентов.

### Проверка

Пользователь без дополнительных объяснений понимает, что при наличии критических инцидентов сначала должен работать с ними и их необходимыми действиями, а при отсутствии критических инцидентов — выбирать действия с наибольшим количеством связанных инцидентов.

## REQ-DEC-024. Решение Product Manager

**Область:** mainJourney
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-024, PM-DEC-149, PM-DEC-191
**Применимость:** Следующий этап

Для MVP основной пользовательский сценарий аналитика внутри Set Mark строится вокруг двух приоритетов, уточнённых Product Manager 27.08.2026:

- **сначала критический риск:** на Дашборде пользователь сразу видит наличие критических инцидентов и связанные с ними необходимые действия; при наличии таких инцидентов они имеют безусловный приоритет;
- **затем регулярное снижение нарушений:** если критических инцидентов нет, пользователь выбирает необходимые действия по количеству связанных инцидентов и работает на уменьшение общего количества нарушений.

Для детализации пользователь может выбрать магазин, кассу, товарную группу либо тип нарушения и перейти к соответствующему списку инцидентов; уточнить выборку поиском и фильтрами; открыть карточку инцидента; изучить исходные данные, понятный результат проверки без технического кода `RA-*`, объяснение, критичность, потенциальный штраф, Контур устранения и рекомендацию; вернуться к списку или аналитике с сохранением выбранного контекста; при необходимости выгрузить текущую выборку в CSV или сформировать PDF выбранного инцидента.

Дополнительные точки входа: из ежедневного email-дайджеста пользователь переходит в Set Mark к списку Инцидентов за предыдущий календарный день с фильтром новых критичных отклонений и контекстом организации; администратор открывает настройки функции для управления подключением, получателями уведомлений и сроком хранения данных; при недостаточных правах, неполных или устаревших данных интерфейс показывает доступный результат и понятное ограничение.

### Проверка

Реализация не заставляет пользователя проходить всю аналитику последовательно: критический путь доступен сразу, а регулярный путь выводит на действия с наибольшим влиянием на количество нарушений.
