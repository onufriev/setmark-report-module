# Ответы Product Manager на вопросы разработки

**Статус:** ответы актуализированы 2026-09-16; открытых продуктовых вопросов в этом документе не осталось.

## 1. Ручной процесс получения данных от True API

Отсутствует описание сценария ручного получения данных об отклонениях от True API.
В документации True API описан процесс получения данных, как процесс из четырех шагов:
- отправка запроса на формирование выгрузки с параметрами, например, диапазон дат
- проверка готовности выполнения до появления статуса
- запрос списка файлов и их статус
- скачивание файлов
  Далее необходимо сохранить/обновить данные в БД.
  Таким образом это асинхронный процесс, который требует мониторинга выполнения.
  Нет возможности по нажатие на кнопку пользователем сразу выполнить результат и оповестить OK, NOK.
  К тому же у True API для каждого метода есть ограничения по частоте вызовов.

Для реализации такой интеграции будет создана очередь заданий для скачивания чего-либо из TrueAPI, т.к. подход для разных типов данных там общий и эта общая реализация может быть полезной в будущем.
Т.е. при ручном обмене пользователь создаёт задание, указывает за какой период ему нужны отклонения.
Далее необходимо отслеживать процесс выполнения задания. Для этого нужен UI и макеты.
Процесс не может быть вечным и будет настраиваемое ограничение по времени его выполнения.

Также возникают такие вопросы:
- Может ли один или разные пользователи создавать задания для скачивания отклонений с разными, похожими или пересекающимися периодами ? Какое поведение системы при таких сценариях ожидается?
- Если на одном из этапов выполнения задания произойдет ошибка, что будет пользователь, как его оповестить?

### Зафиксированное поведение

- Нажатие кнопки создаёт один логический фоновый `SyncRun`; синхронный результат `OK/NOK` не ожидается.
- Пользователь выбирает период: с последней успешной синхронизации или последние 1, 7, 30, 90 календарных дней, включая текущий. При первом запуске доступны фиксированные периоды, в том числе 7 дней; обязательной загрузки за 90 дней нет. Произвольный диапазон не задаётся. Периоды больше допустимого окна True API система разбивает самостоятельно. Фильтр относится к дате регистрации отклонения, не к дате операции; режим «с последней» повторно включает весь календарный день последнего успеха.
- Для одного ИНН одновременно допускается только один активный `SyncRun`. Повторная попытка другого или того же пользователя не создаёт и не ставит в очередь дублирующее задание: интерфейс открывает существующий запуск и показывает его инициатора и состояние. Разные ИНН обрабатываются независимо.
- После запуска интерфейс подтверждает создание задания; в настройках True API по каждому ИНН доступны текущее состояние и результат последнего обращения с временем. История запусков не нужна. При подключении организации можно добавить ИНН либо выбрать ранее добавленный; отдельного справочника организаций и управления большим списком в MVP нет.
- Временные сетевые ошибки повторяются автоматически до настраиваемого конечного предела. При истечении авторизации пользователь получает действие повторной авторизации с УКЭП; при исчерпании квоты видит состояние ожидания. Окончательная или частичная ошибка содержит время, понятную причину и дальнейшую рекомендацию. Выгрузки и квоты по разным ИНН независимы; глобальный ограничитель не вводится.
- Один общий тайм-аут всего `SyncRun` не используется: настраиваемое ограничение применяется к ожиданию отдельного этапа с учётом `timeoutSecs` True API. Состояния ожидания авторизации и квоты не завершаются ошибкой только из-за общей длительности процесса.
- Успешно импортированные части при частичной ошибке не откатываются, но курсор последней полностью успешной синхронизации не продвигается.

Основания: `PM-DEC-210`–`PM-DEC-218`, `PM-DEC-223`–`PM-DEC-224`; подробный workflow — `docs/product-definition/gis-mt-deviations-ingestion-v0.1.md`.


## 1.1. Справочники и фильтры выгрузки

В загружаемых данных об отклонениях нет ссылок на справочники "Категории отклонений", "Виды отклонений", "Результаты выявления отклонений",
поля содержат не коды из этих справочников, а наименования. \
Загрузка/обновление справочников "Категории отклонений", "Виды отклонений", "Результаты выявления отклонений" 
могут быть полезны при указании параметров когда выполняется заказ на выгрузку отклонений (8.3.15), т.к.
в аргументах могут передаваться именно коды из этих справочников. \
> Вопрос: предполагается ли загрузка отклонений с использованием фильтров по категориям, видам, результатам?
Если да, то синхронизация справочников, как и хранение в БД понадобится, иначе - нет.

### Зафиксированное поведение

В MVP загрузка **не фильтруется** по категориям, видам или результатам: Set Mark запрашивает все доступные отклонения по каждой применимой товарной группе. Пользователь эти фильтры не задаёт. `params="{}"` используется только после подтверждения на real-API spike, что это означает отсутствие бизнес-фильтрации.

Динамический справочник не нужен для формирования задания. Сопоставление `наименование → код` откладывается до этапа анализа. Для MVP обязательны исходные наименования; отсутствие кодов не блокирует импорт.

Основание: `PM-DEC-219`, `REQ-DATA-001`.

## 2. Типы полей выгрузки

В спецификации True API отсутствует информация о типах полей в выгружаемой информации об отклонениях.
Только для двух полей: "Дата и время регистрации отклонения" и "Дата и время выполнения операции, в результате которой было выявлено отклонение" можно точно сказать, 
что там дата-время. Для остальных полей можно только догадаться по примерам, что там String, Integer, Decimal. 

> Информация нужна, чтобы создать оптимальную и правильную схему БД для хранения отклонений необходимо знать информацию о типах полей.

### Зафиксированное поведение

Все колонки CSV сохраняются как исходные строки в привязке к импорту. Типизированное представление требуется только для полей, используемых MVP; неиспользуемые поля специально не типизируются. `GTIN` и `ИНН` остаются строками для сохранения ведущих нулей. Значения дат без маркера зоны в MVP интерпретируются как `Europe/Moscow` по решению Product Manager; исходные строки сохраняются без изменения. Это допущение, а не подтверждённый факт о ГИС МТ.

Точные формат, кодировка, разделитель и обязательность колонок проверяются на real-API spike и закрепляются fixtures/contract tests. «Номер отклонения» — обязательная непрозрачная строка, формат UUID не требуется. Всю исходную строку CSV необходимо хранить, но весь ZIP/CSV-файл как отдельный объект хранить не обязательно.


## 3. Уникальность и обновление отклонений

Также отсутствует информация об уникальности полей.
   Является ли поле "Номер отклонения" уникальным, чтобы его использовать для обновления существующих данных?
   Или уникальность обеспечивается неким составным ключом, например, "ИНН" + "Номер отклонения" ?

> Информация нужна, чтобы процесс обновления данных выполнялся корректно.

### Зафиксированное поведение

Глобальная уникальность «Номера отклонения» между организациями не считается гарантированной. Persistence/idempotency key MVP — `(requested_inn, external_deviation_id)`, где `external_deviation_id` — непрозрачная строка из поля «Номер отклонения». Дата, КМ, ККТ и другие поля в ключ не входят.

Первый полученный снимок отклонения неизменяем. Повтор той же пары не создаёт вторую запись и второй downstream event. Если для той же пары приходит строка с другими данными, исходное отклонение не изменяется; отличающаяся исходная строка фиксируется для технической диагностики. Отдельная пользовательская сущность или интерфейс аномалий в MVP не нужны.
