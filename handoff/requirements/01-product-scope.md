# Продукт, цели и границы

Этот документ собран из канонического каталога `requirements/`. Он предназначен для чтения командой реализации и не заменяет канонические требования.

## MVP

### REQ-DEC-143. Решение Product Manager

В MVP продукт помогает своевременно обнаружить отклонения, локализовать их по объектам и открыть собранные и сопоставленные данные инцидента. Автоматическое объяснение причины, рекомендации, необходимые действия, отдельная аналитика, экспорты и уведомления развивают продуктовую ценность на следующем этапе.


**Как проверить**
Реализация соответствует решению PM-DEC-158.

### REQ-DEC-004. Продуктовый контекст

Утверждён продуктовый контекст. Бизнес-цель уточнена Product Manager 27.08.2026:

- Проблема: ответственные сотрудники торговой сети слишком поздно обнаруживают отклонения при продаже маркированных товаров; нарушения накапливаются, а их причины и место устранения трудно определить по разрозненным данным.
- Продуктовая граница: новая функция внутри существующего продукта Set Mark, использующая данные и механизмы Set Mark; это не самостоятельный продукт и не автономный программный модуль.
- Пользователи: любые сотрудники, ответственные за разбор нарушений маркировки. В крупной сети это может быть специализированный аналитик, а в небольшой компании — владелец, руководитель, товаровед или администратор. В MVP доступ определяется доступом к текущему Журналу нарушений без новой ролевой модели; привилегии SetCentrum относятся к следующему этапу.
- Результат MVP: пользователь видит отклонение, локализует его и изучает собранные и сопоставленные исходные данные. Автоматическое объяснение причины, оценка потенциального штрафа и рекомендация относятся к следующему этапу.
- Бизнес-цель: как можно раньше выявлять отклонения маркировки и предоставлять данные для их разбора. Объяснение причин и компенсирующие действия для предотвращения повторения развивают эту цель на следующем этапе. Снижение вероятности проверок и штрафов является ожидаемым, но не гарантированным эффектом действий клиента.
- Границы: применяются утверждённые границы MVP из Q-002.
- Коммерческая модель: пока не определена и этим решением не фиксируется.


**Как проверить**

Реализация соответствует решению PM-DEC-004 и явно связывает ценность функции со снижением риска получения штрафов за нарушения маркировки.

### REQ-PC-001. Назначение продукта

Новая функция Set Mark должна предоставить ритейлеру централизованный инструмент мониторинга отклонений маркировки. В MVP инструмент обеспечивает обнаружение, локализацию и просмотр сопоставленных исходных данных; оперативные уведомления и рекомендации по исправлению относятся к следующему этапу.


**Как проверить**

Назначение MVP подтверждается сквозным сценарием мониторинга от агрегатов до карточки сопоставленных данных; уведомления и рекомендации проверяются на следующем этапе.

### REQ-PC-002. Контекст Set Mark

Функция создаётся внутри Set Mark — продукта экосистемы Set Retail 10 для контроля розничной продажи маркированного товара.


**Как проверить**

Описание функции и границы интеграций явно фиксируют её как часть Set Mark и связывают с Set Retail 10.

### REQ-DEC-193. Два законченных продуктовых этапа MVP

MVP формируется двумя законченными продуктовыми этапами, каждый из которых пригоден для самостоятельного использования и отдельного выпуска. Этап 1 «Контроль отклонений Честного знака» включает реальное подключение ЛК ЧЗ через ЭЦП по ИНН, ручную синхронизацию, отбор кассовых отклонений, Обзор, список Инцидентов, карточку с исходными данными ЧЗ, поиск, периоды, фильтры, группировки, критичность, все необходимые состояния, ограничения страны, лицензии и версии, защиту от дублей, производительность и отсутствие влияния на текущий ЖН. Этап 2 «Обогащённый разбор инцидента» добавляет сопоставление с ЖН, чеком, проверками и историческими настройками, поиск марки по вхождению с учётом криптохвоста и окна ±5 минут, параллельные результаты онлайн ЧЗ и Set Mark, результат ЛМ ЧЗ, решение и действие кассы, визуализацию настроек и обработку отсутствующих источников. После этапа 2 достигается полный состав MVP. Каждый этап включает полноценные ошибки, права, безопасность, эксплуатационную документацию и отдельную приёмку на реальном подключении; незаконченные доступные экраны и заглушки не допускаются. Автоматический анализ и рекомендации остаются следующим этапом развития.


**Как проверить**
Реализация соответствует решению PM-DEC-208.

### REQ-DEC-129. Решение Product Manager

MVP включает существующий Журнал нарушений без изменения его текущих функций; Обзор с основными агрегатами и распределением отклонений; список Инциденты с поиском, фильтрами и группировками; карточку инцидента с данными Честного знака, Журнала нарушений, чека, проверок и настроек; настройки подключения True API, критичности видов отклонений и ручной синхронизации. Результаты автоматического анализа, рекомендации и CSV текущей выборки относятся к следующему этапу. Отдельные разделы Необходимые действия и Аналитика, PDF и ежедневные уведомления также не входят в MVP.


**Как проверить**
Реализация соответствует решению PM-DEC-144.

**Как проверить**
Реализация соответствует решению PM-DEC-125.

### REQ-GS-003. Географическая применимость MVP

MVP функции применяется только для организаций, у которых страна в SetCentrum определена как `RU`. Для организаций других стран разделы Мониторинга, интеграция с «Честным знаком», фоновые процессы и подключение ЭЦП не запускаются. Остальные возможности Set Mark продолжают работать без изменений.


**Как проверить**

Для организации `RU` доступны предусмотренные лицензионным состоянием функции. Для организации с любой другой страной Мониторинг и связанные процессы отсутствуют, а остальные разделы Set Mark остаются доступны по собственным правилам.

### REQ-GS-004. Регуляторный контекст и квалификация риска

Отклонения, зарегистрированные в ГИС МТ, используются государственным контролем для выявления индикаторов риска и планирования контрольных мероприятий. Официальное описание индикаторов риска и их применения опубликовано Роспотребнадзором: `https://13.rospotrebnadzor.ru/content/o-perechne-indikatorov-riska-narusheniya-obyazatelnyh-trebovaniy-pri-osushchestvlenii`.

Практическое использование данных ГИС МТ для наблюдений, предостережений и контрольных закупок подтверждается опубликованной Роспотребнадзором статистикой: `https://77.rospotrebnadzor.ru/index.php/press-centr/186-press-centr/14632-o-kontrole-za-oborotom-tovarov-podlezhashchikh-markirovke-sredstvami-identifikatsii-chestnyj-znak`.

С 1 сентября 2026 года Федеральный закон от 02.05.2026 № 120-ФЗ предусматривает автоматическое привлечение к административной ответственности по отдельным составам нарушений на основании данных ГИС МТ. Официальное разъяснение: `https://zpp.rospotrebnadzor.ru/news/federal/576342`.

Срабатывание индикатора риска само по себе не является доказанным нарушением и не означает автоматического штрафа. Признак «риск автоштрафа» присваивается только тем типам инцидентов, которые соответствуют действующему перечню составов автоматической ответственности. Остальные инциденты могут влиять на индикаторы риска и вероятность проверки, но не должны маркироваться как основание для автоштрафа.


**Как проверить**

Для каждого типа инцидента отдельно определено, относится ли он к действующему механизму автоштрафа, индикатору риска либо ни к одной из этих категорий. Интерфейс и материалы не отождествляют индикатор риска с установленным нарушением.

### REQ-DEC-003. Границы MVP

В MVP входят:

- получение отклонений через True API;
- все отклонения розничной реализации и выбытия;
- сопоставление с данными Set Mark и SetRetail по полному коду маркировки;
- Обзор с основными агрегатами и распределением отклонений;
- список «Инциденты» с поиском, фильтрами и группировками;
- карточка инцидента с данными Честного знака, Журнала нарушений, чека, проверок и настроек;
- настройка подключения True API, критичности видов отклонений и ручной синхронизации;
- сохранение существующих функций Журнала нарушений без изменений.

В MVP не входят:

- отклонения производства, импорта, логистики и ввода в оборот;
- блокирование продажи в реальном времени;
- автоматическое исправление настроек или данных;
- автоматическое создание обращений в ГИС МТ;
- ML-прогнозирование нарушений;
- анализ процессов, не относящихся к розничному выбытию;
- мобильное приложение;
- пересчёт ранее созданных инцидентов при изменении правил;
- каналы и периодичность уведомлений сверх минимального ежедневного сценария;
- управление задачами и контроль выполнения исправлений.
- автоматический результат анализа, объяснение причины и рекомендации;
- отдельные разделы «Необходимые действия» и «Аналитика»;
- CSV и PDF;
- ежедневные уведомления и настройка их получателей;
- настройка срока хранения через новый интерфейс.

Ключевой результат MVP: пользователь видит отклонение Честного знака и собранные для его разбора данные кассового процесса в одной карточке.

Критерий успеха MVP: успешный запуск функции минимум у трёх клиентов. Дополнительная детализация критериев успешности отдельного клиентского запуска на данном этапе не устанавливается.


**Как проверить**

Реализация соответствует решениям PM-DEC-003 и PM-DEC-105, описывает границы MVP на уровне продуктовых возможностей и фиксирует минимальное количество успешных клиентских запусков.

### REQ-GS-001. Целевой результат

MVP должен сокращать задержку между возникновением отклонения маркировки и его обнаружением, предоставляя централизованный Обзор, список инцидентов и собранные данные источников в карточке.


**Как проверить**

Основной пользовательский путь позволяет обнаружить отклонение, локализовать его и изучить связанные данные ЧЗ, ЖН, чека, проверок и настроек.

### REQ-DEC-101. Демонстрационный режим относится к следующему этапу

Демонстрационный режим Set Mark для клиента без установленного продукта или без полного лицензионного доступа не входит в MVP и относится к следующему этапу развития. Его требования должны находиться в каноническом каталоге `requirements/`, а не только в `reference-materials`.


**Как проверить**
Состав MVP не включает усечённый Обзор, лицензионные заглушки, подключение ЭЦП и сбор данных для клиента без установленного Set Mark; эти возможности явно помечены как следующий этап.

### REQ-DEC-052. Функциональность входит в коробочное решение Set Mark

Объектом продажи является коробочное решение Set Mark.

Функциональность «Мониторинг и анализ нарушений» входит в коробочное решение Set Mark и отдельно не лицензируется.

- Для действующих клиентов Set Mark функциональность предоставляется в составе используемого коробочного решения.
- Для новых клиентов функциональность предоставляется в составе приобретаемого коробочного решения.
- Отдельная единица лицензирования, отдельный тариф и отдельная стоимость для функциональности не устанавливаются.
- Настоящее требование не определяет стоимость коробочного решения Set Mark в целом.

Торговая сеть, магазин/торговая точка, касса, инцидент, кассовая операция и код маркировки являются объектами предметной области, эксплуатации и анализа. Они не являются автоматически объектами продажи и не образуют коммерческую иерархию в рамках текущего MVP.


**Как проверить**

Коммерческое описание продукта и пользовательские материалы представляют функциональность «Мониторинг и анализ нарушений» как часть коробочного решения Set Mark, не выделяют её в отдельную лицензию и не указывают отдельную стоимость.

### REQ-MKT-001. Область и назначение оценки

**Дата среза:** 2026-09-01

Оценка определяет потенциальный новый валовый годовой доход от допродажи лицензий Set Mark действующим клиентам с кассовыми лицензиями SetRetail. Она используется для проверки коммерческого потенциала продукта и не является утверждённым прайс-листом или прогнозом продаж.

В расчёт включаются только рабочие клиенты с подтверждённой страной `RU`, активной кассовой лицензией и положительным значением поля «Используемое количество». Тестовые контуры, клиенты других стран, лицензии с истёкшим сроком и клиенты без подтверждённой страны исключаются.

### REQ-MKT-002. Источники и правила сопоставления

Использованы три предоставленных среза:

- `Клиенты с кассовой лицензией.xlsx` — кассовые лицензии и количество используемых касс;
- `Текущие клиенты SetMark.xlsx` — типы лицензий Set Mark и количество использующих их магазинов;
- `Клиенты по странам.xlsx` — страна клиента.

Кассовые лицензии и лицензии Set Mark сопоставляются по точному `Set ID`. Страна присоединяется по точному совпадению названия клиента, поскольку файл стран не содержит `Set ID`. Клиенты, для которых такое сопоставление не выполнено, не считаются клиентами `RU` и не входят в денежную оценку.

После очистки получено:

- 515 активных производственных RU-клиентов с используемыми кассами;
- 92 из них уже имеют активную лицензию Set Mark;
- 423 клиента составляют новый адресный пул;
- текущее проникновение Set Mark в очищенной базе — `92 / 515 = 17,9%`;
- потенциал роста по числу новых клиентов — 423 сети, или 82,1% очищенной базы.

### REQ-MKT-003. Пересчёт касс в магазины

Первичный файл содержит количество касс, тогда как Set Mark лицензируется на магазин. Для пересчёта используется медианное фактическое отношение используемых касс к использующим Set Mark магазинам у действующих RU-клиентов, присутствующих в обоих лицензионных срезах.

- размер пригодной выборки: 73 клиента;
- медианное отношение: 4,23 кассы на магазин;
- расчёт для каждой сети: `max(1; округление вверх(используемые кассы / 4,23))`;
- в новом адресном пуле: 25 070 используемых касс;
- оценочное количество магазинов: 6 143.

Медиана выбрана вместо среднего из-за значительных выбросов и неполной активации лицензий в отдельных сетях. Оценка должна пересчитываться при появлении прямого реестра магазинов потенциальных клиентов.

### REQ-MKT-004. Коммерческие допущения

- Set Mark продаётся отдельно по каждому типу лицензии.
- Оценочная цена одного типа лицензии — 4 000 рублей с НДС за магазин в год.
- Если сеть принимает решение о покупке, лицензия распространяется на 100% её оценочных магазинов.
- Вероятность покупки для каждой новой сети — 80%.
- Считается валовый доход без скидок, партнёрских условий, бесплатных лицензий и стоимости внедрения.
- Учитывается только новый доход; существующие клиенты Set Mark и их текущие лицензии из денежного потенциала исключены.

Поскольку в данных нет товарного профиля потенциальных клиентов, распределение типов оценивается по фактическому количеству используемых лицензий у активных RU-клиентов Set Mark:

- «Продовольственные товары» — 3 625 лицензий, или 33,2% количества трёх основных типов;
- «Непродовольственные товары» — 3 206 лицензий, или 29,3%;
- `Alco` — 4 098 лицензий, или 37,5%.

Для учёта того, что один магазин может использовать несколько типов, по каждому текущему клиенту количество магазинов оценивается как максимальное используемое количество среди трёх основных типов. Получено 6 180 магазинов и 10 929 используемых лицензий типов, то есть в среднем 1,768 типа лицензии на магазин.

Специализированные лицензии для других стран, интеграционный модуль Честного Знака и Set Mark Centrum Enterprise в эту оценку не включаются.

### REQ-MKT-006. Ограничения оценки

Оценка является экспресс-моделью. ### REQ-GS-002. Раннее выявление и снижение последствий нарушений

Главная цель функции — как можно раньше выявлять нарушения маркировки, объяснять их причины и предлагать компенсирующие действия, позволяющие ограничить масштаб и последствия нарушений и предотвратить их повторение. Функция не устраняет нарушения автоматически и не гарантирует снижение штрафов. Снижение вероятности проверок и штрафов является ожидаемым бизнес-эффектом действий клиента.

Функция должна способствовать достижению этой цели в двух режимах:

1. **Критический режим** — как можно раньше выявлять инциденты, для которых возможен автоматический штраф, и сразу показывать действия, необходимые для устранения причины и предотвращения повторения.
2. **Регулярный режим** — при отсутствии критических инцидентов снижать общее количество нарушений, в том числе влияющих на индикаторы риска «Честного знака», выбирая в первую очередь действия, способные предотвратить наибольшее количество инцидентов. Цель регулярного режима — снижать вероятность последующих проверок и штрафов.

Объяснение причин нарушения и формирование необходимых действий являются прямым результатом функции; снижение регуляторных последствий возникает после выполнения этих действий клиентом.


**Как проверить**

Продуктовое описание и пользовательские сценарии явно разделяют критический и регулярный режимы: критические инциденты обрабатываются первыми, а при их отсутствии действия приоритизируются по количеству предотвращаемых инцидентов.
