# Предметная модель, состояния и бизнес-правила

Этот документ собран из канонического каталога `requirements/`. Он предназначен для чтения командой реализации и не заменяет канонические требования.

## MVP

### REQ-DEC-136. Решение Product Manager

В MVP инцидент содержит отклонение Честного знака и сопоставленные данные Журнала нарушений, чека, проверок и настроек. Результат анализа RA-01–RA-05, установленная причина, рекомендация, Контур устранения, потенциальный штраф, история рекомендации и экспортное представление относятся к следующему этапу.


**Как проверить**
Реализация соответствует решению PM-DEC-151.

### REQ-DEC-091. Решение Product Manager

Инцидент хранит штрихкод, артикул, наименование товара, номер чека или идентификатор операции и источник проверки. Все эти поля относятся к той же операции, что полный код маркировки и временная метка инцидента, и используются согласованно в карточке и точном поиске. Использование полей в CSV относится к следующему этапу.


**Как проверить**
Реализация соответствует решению PM-DEC-094.

### REQ-BO-002. Поисковые данные товара и операции

Инцидент содержит штрихкод, артикул, наименование товара, номер чека или идентификатор операции и источник проверки. Поля относятся к операции, вызвавшей отклонение, и доступны для поиска и карточки. Экспорт этих полей в CSV относится к следующему этапу.


**Как проверить**

Поля относятся к той же операции, что код маркировки и временная метка инцидента.

### REQ-DEC-035. Решение Product Manager

Каждый инцидент относится ровно к одному типу нарушения из каталога и учитывается в соответствующей разбивке один раз.

Критическим считается инцидент вида, отмеченного критичным в визуализированной настройке критичности видов отклонений. Денежное значение потенциального штрафа и сущность «Необходимое действие» относятся к следующему этапу.


**Как проверить**
Реализация соответствует решениям PM-DEC-036, PM-DEC-054 и PM-DEC-055.

### REQ-DEC-006. Модель сущностей и состояний

Для MVP утверждена следующая модель сущностей:

- Инцидент — центральная сущность; одно отклонение True API создаёт один инцидент.
- Отклонение True API хранится в инциденте как неизменяемый снимок исходных данных.
- Код маркировки хранится полностью и может участвовать в нескольких операциях и инцидентах.
- Кассовая операция включает операцию, вызвавшую отклонение, и доступную историю продаж, возвратов и отмен.
- Проверка марки включает результаты Set Mark, онлайн-проверки «Честного знака» и ЛМ ЧЗ.
- Конфигурация магазина содержит настройки, относящиеся к моменту проверки, либо явно обозначается как актуальная конфигурация, не являющаяся историческим доказательством.
- Вид отклонения и его критичность определяются по исходным данным Честного знака и визуализированной настройке.

Результат анализа `RA-01`–`RA-05`, потенциальный штраф, Контур устранения, объяснение, рекомендация, версия правил анализа и состояния выполнения анализа относятся к следующему этапу.

Ручные пользовательские состояния, включая «Новый» и «Просмотрен», не вводятся.

Статусы «В работе» и «Исправлен», назначение ответственного и контроль выполнения также не вводятся в MVP.


**Как проверить**

Реализация соответствует решениям PM-DEC-006 и PM-DEC-010 и не вводит дополнительные бизнес-сущности, ручные пользовательские состояния или состояния управления задачами. Для каждого впервые сохранённого отклонения технический механизм долговечной идемпотентной доставки гарантирует создание ровно одного инцидента; повторная доставка не создаёт дубликат, а сбой корреляции не теряет обязательство обработки.

### REQ-BO-001. Связь отклонения с внутренними данными

Отклонение из Честного знака должно сопоставляться с записью журнала нарушений Set Mark по коду маркировки и временной метке; при отсутствии записи журнала используется последний успешный результат проверки в Честном знаке, если он доступен.


**Как проверить**

Для отклонения отображается связанная запись Set Mark либо явно указан использованный результат проверки Честного знака.

### REQ-DEC-131. Решение Product Manager

В MVP система собирает и сопоставляет факты по отклонению, но не присваивает пользовательский результат автоматического анализа и не формирует рекомендацию. Правила результатов анализа, объяснения причин и рекомендаций реализуются на следующем этапе.


**Как проверить**
Реализация соответствует решению PM-DEC-146.

### REQ-DEC-125. Решение Product Manager

В MVP настройка подключения и ручной запуск True API доступны при действующей лицензии, лицензионном несоответствии и в течение 10-дневного льготного периода. Для этих операций состояния несоответствия и льготного периода не создают дополнительного предупреждения или ограничения. После окончания льготного периода, при подтверждённом состоянии «лицензии никогда не было» и при неизвестном статусе без достоверной истории настройка и запуск недоступны. При недоступности Set Agent доступ рассчитывается по последнему достоверному сохранённому состоянию и дате окончания. Получение данных без лицензионного доступа относится к следующему этапу.


**Как проверить**
Реализация соответствует решению PM-DEC-140.

### REQ-DEC-085. Решение Product Manager

Доступность вычисляется в едином порядке для UI, API и фоновых процессов: 1) нормализовать `setmark.country`; 2) применить ограничение страны, полностью исключив Мониторинг для не `RU`; 3) проверить базовое право просмотра Журнала; 4) определить состояние лицензии по текущим данным и достоверной истории; 5) применить приоритет истечения лицензии над лицензионным несоответствием; 6) выбрать полный или ограниченный набор функций; 7) перед каждой операцией дополнительно проверить требуемую функциональную или административную привилегию. Одинаковые входные данные должны приводить к одинаковому результату во всех каналах.


**Как проверить**
Реализация соответствует решению PM-DEC-088.

### REQ-DEC-082. Решение Product Manager

Журнал нарушений и Мониторинг маркировки используют одну общую лицензию Set Mark; отдельные лицензии для этих функций не вводятся. Отдельного типа «пробная лицензия» нет: обычная лицензия с ограниченным сроком считается действующей до даты окончания, после чего применяются общий льготный период и ограничения. Лицензионное несоответствие возможно только при наличии хотя бы одной действующей лицензии и включает недостаточное количество лицензий или неподходящую товарную категорию. Ноль действующих лицензий не является несоответствием: состояние определяется как льготный период, завершённый льготный период, «лицензии никогда не было» либо неизвестное состояние согласно достоверной истории. Истечение лицензии имеет приоритет над признаком лицензионного несоответствия.


**Как проверить**
Реализация соответствует решению PM-DEC-085.

### REQ-DEC-067. Решение Product Manager

Если у клиента есть хотя бы одна действующая лицензия Set Mark, но она относится не к требуемой товарной категории, система классифицирует ситуацию как лицензионное несоответствие. Функции и данные Set Mark остаются полностью доступными; система показывает понятное неблокирующее предупреждение о несовпадении товарной категории и предлагает приобрести лицензию нужной категории.


**Как проверить**
Реализация соответствует решению PM-DEC-070.

### REQ-DEC-066. Решение Product Manager

Если у клиента есть хотя бы одна действующая лицензия Set Mark, но приобретённого количества лицензий недостаточно для всех магазинов сети, система классифицирует ситуацию как лицензионное несоответствие. Функции и данные Set Mark остаются полностью доступными для всех магазинов; система показывает понятное неблокирующее предупреждение о недостаточном количестве лицензий и предлагает докупить недостающее количество.


**Как проверить**
Реализация соответствует решению PM-DEC-069.

### REQ-DEC-065. Решение Product Manager

Если Set Agent недоступен, но в SetCentrum сохранена достоверная дата окончания последней активной лицензии Set Mark, система рассчитывает состояние доступа по этой дате: до окончания лицензии сохраняет полный доступ, затем применяет льготный период ровно 10 календарных дней, после которого включает предусмотренные ограничения. Одновременно система должна показывать предупреждение, что актуализировать сведения о лицензии через Set Agent не удалось.


**Как проверить**
Реализация соответствует решению PM-DEC-068.

### REQ-DEC-062. Решение Product Manager

После окончания лицензии Set Mark действует льготный период продолжительностью ровно 10 календарных дней. Длительность льготного периода не настраивается клиентом. Расчёт выполняется в часовом поясе SetCentrum; ограничения включаются сразу после завершения десятого календарного дня и применяются при создании новой пользовательской сессии.


**Как проверить**
Реализация соответствует решению PM-DEC-065.

### REQ-DEC-036. Решение Product Manager

При выборе нескольких типов отклонения показываются инциденты хотя бы одного выбранного типа. Одновременно включённые фильтры применяются совместно. Правила приоритизации необходимых действий относятся к следующему этапу.


**Как проверить**
Реализация соответствует решению PM-DEC-037.

### REQ-DEC-031. Решение Product Manager

При онлайн-проверке Честный знак возвращает исходные данные и признаки о коде маркировки, а не итоговое решение «продавать / не продавать». Кассовое ПО применяет к этим данным действующие правила запрета и формирует собственное решение о допустимости продажи. Инцидент должен раздельно хранить и показывать исходные признаки ответа Честного знака, режим проверки, применённую версию правил, решение кассового ПО и фактическое действие кассы. Формулировки, приписывающие Честному знаку итоговое разрешение или запрет продажи, не используются.


**Как проверить**
Реализация соответствует решению PM-DEC-031.

### REQ-DEC-007. Решение Product Manager

Для MVP утверждены следующие бизнес-правила:

- при получении одного отклонения True API создаётся один инцидент;
- сопоставление выполняется по вхождению кода маркировки с учётом окна времени ±5 минут;
- исходные данные онлайн-проверки ЧЗ и проверки Set Mark отражаются как параллельные результаты, после которых отдельно показывается решение кассового ПО и фактическое действие кассы;
- результат ЛМ ЧЗ показывается, если использовался офлайн-сценарий;
- вид отклонения и его критичность показываются по исходным данным и настройке критичности.

Присвоение `RA-01`–`RA-05`, автоматическое объяснение причины, расчёт потенциального штрафа, Контур устранения и рекомендация относятся к следующему этапу.


**Как проверить**
Реализация соответствует решениям PM-DEC-007, PM-DEC-031 и PM-DEC-056.

### REQ-BR-001. Корреляция отклонений

Система должна сопоставлять отклонения Честного знака с записями журнала нарушений Set Mark по коду маркировки и временной метке.


**Как проверить**

Для каждого сопоставленного отклонения доступны использованные ключи корреляции и связанная запись журнала.

### REQ-BR-002. Последовательность онлайн- и офлайн-проверки

В карточке кассовой проверки система должна раздельно показывать параллельные результаты онлайн-проверки ЧЗ и проверки Set Mark. Если онлайн-ответ ЧЗ отсутствовал и применялся ЛМ ЧЗ, его результат показывается как последующий офлайн-сценарий перед решением кассового ПО.


**Как проверить**

Карточка различает результаты онлайн ЧЗ и Set Mark, переход к ЛМ ЧЗ при его наличии, решение кассового ПО и фактическое действие кассы без автоматического аналитического вывода.

### REQ-BR-003. Справочник отклонений

Категории, виды и результаты отклонений должны идентифицироваться по справочникам True API v704.0, страницы 1229–1234, до подключения более актуального официального справочника.


**Как проверить**

Код и название отклонения в каталоге соответствуют зарегистрированному снимку True API v704.0.

### REQ-DEC-123. Решение Product Manager

Для первой и последующих синхронизаций True API применяются состояния: «Данные ещё не загружены» до первого запуска; «Синхронизация выполняется» во время запроса без возможности параллельного повторного запуска; успешная загрузка с отклонениями; успешный пустой ответ «За выбранный период отклонения не найдены»; ошибка с причиной, временем и рекомендацией попробовать получить данные позднее без кнопки «Повторить»; устаревшие данные с датой последнего успешного получения; «Данные получены не по всем ИНН», если успешный результат отсутствует хотя бы для одного из подключённых ИНН. Другие варианты не называются частичной загрузкой.


**Как проверить**
Реализация соответствует решению PM-DEC-138.

### REQ-DEC-083. Решение Product Manager

Для клиента RU после проверки прав применяются следующие состояния. При действующей лицензии доступ полный. При лицензионном несоответствии доступ полный с неблокирующим предупреждением. В течение 10-дневного льготного периода доступ полный с предупреждением и остатком срока. При недоступности Set Agent и наличии достоверной даты окончания состояние пересчитывается по этой дате, включая льготный период, с предупреждением о невозможности актуализации. «Лицензии никогда не было» назначается только при явном подтверждении полной истории Set Agent. Предупреждения должны отличаться от ошибок доступа, объяснять конкретное состояние и не блокировать функции при полном доступе.

Усечённый Обзор, лицензионные заглушки и подключение ЭЦП при отсутствии полного лицензионного доступа относятся к следующему этапу по REQ-DEC-105 и не являются поведением MVP.


**Как проверить**
Реализация соответствует решению PM-DEC-086.

### REQ-DEC-038. Решение Product Manager

В блоке «Состояние данных» показываются только два сигнала:

1. Результат последнего обращения в «Честный знак» за отчётом — успешно или с ошибкой — с датой и временем обращения.
2. Наличие или отсутствие связи с Set Centrum.

Без связи с Set Centrum анализ инцидентов невозможен. Проценты полноты, количество пропущенных записей и оценка качества данных в этом блоке не показываются.


**Как проверить**
Реализация соответствует решению PM-DEC-039.

### REQ-DEC-009. Решение Product Manager

Для MVP утверждены следующие ошибки, пустые и недоступные состояния:

- Если нарушений за выбранный период нет, система показывает сообщение «Нарушения не обнаружены».
- Если данным не соответствует текущий набор фильтров, система сообщает об отсутствии результатов и предлагает действие «Сбросить фильтры».
- Во время загрузки система показывает индикатор загрузки и не выдаёт устаревший результат за актуальный.
- При задержке обновления данных система показывает предупреждение и время последнего успешного обновления.
- Если часть источников обогащения недоступна, система показывает доступные данные и явно отмечает недоступные, но не называет это частичной загрузкой True API.
- Если данных недостаточно для сопоставления, карточка перечисляет отсутствующие источники без присвоения результата анализа.
- Если вид отклонения неизвестен, карточка показывает исходное значение Честного знака без присвоения результата анализа.
- При ошибке получения или сопоставления система показывает понятное описание и идентификатор инцидента.

### REQ-DEC-053. Расчёт потенциального штрафа

Потенциальный штраф рассчитывается по точной формуле применимой нормы КоАП, действующей на дату кассовой операции. Значение отражает возможный финансовый риск и не означает, что штраф фактически назначен.

На Обзоре показатель агрегируется только по инцидентам выбранного пользовательского периода и подписывается как расчётная оценка за этот период, а не прогноз или сумма уже назначенного штрафа.

- Если норма устанавливает фиксированную ставку за единицу нарушения, потенциальный штраф рассчитывается как ставка, умноженная на количество единиц, к которым применяется состав.
- Если размер санкции зависит от накопленного количества нарушений за нормативный период, штраф рассчитывается один раз на соответствующий нормативный объект и период. Связанные инциденты участвуют в определении достигнутого порога, но один и тот же штраф не суммируется по каждому инциденту.
- При поступлении новых инцидентов в незавершённом нормативном периоде текущий потенциальный штраф пересчитывается по фактически достигнутому порогу.
- Агрегированный потенциальный штраф на Дашборде является суммой уникальных рассчитанных потенциальных штрафов и не допускает двойного учёта одного состава за один нормативный объект и период.


**Как проверить**

Для состава со ставкой за единицу сумма соответствует ставке и количеству единиц. Для накопительного состава несколько связанных инцидентов формируют один расчёт штрафа за нормативный объект и период; при переходе на следующий порог сумма пересчитывается, но не умножается на количество связанных инцидентов.
