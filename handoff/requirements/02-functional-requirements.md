## Функциональные требования

## REQ-DEC-090
**Применимость:** MVP1

В объединённом наборе сохраняются требования обратной связи ПетШоп: одно поле выполняет точный поиск по одному или нескольким штрихкодам, артикулам и полным кодам маркировки через запятую по логике «ИЛИ»; фильтр позволяет выбрать несколько магазинов, выбрать все или сбросить выбор и объединяется с другими группами фильтров по логике «И»; CSV формируется только по текущей выборке, содержит утверждённые 23 колонки в установленном порядке, кодируется в UTF-8 и корректно экранирует текстовые значения. Массовый поиск и CSV недоступны в ограниченном режиме без лицензии.

## REQ-DEC-080
**Применимость:** MVP1

В состояниях «лицензии никогда не было», «льготный период закончился» и «статус неизвестен без достоверной истории» пользователю доступны усечённый Обзор и штатная Аналитика. При наличии данных Обзор повторяет существующие элементы полного режима: четыре агрегированных показателя «Всего инцидентов», «Критические», «Потенциальный штраф» и «Подтверждённые нарушения», а также блок «Инциденты по типам нарушений». Остальные окна полного Обзора скрываются без замены новыми специальными виджетами. Обзор и Аналитика не показывают строки или карточки инцидентов и не содержат переходов к деталям, рекомендаций, причин, чеков, настроек или результатов сопоставления. «Инциденты» и «Необходимые действия» остаются видимыми в навигации, но открывают лицензионные заглушки без реальных деталей. Журнал нарушений недоступен и располагается последним пунктом меню Set Mark. CSV, PDF, массовый поиск, ежедневные уведомления и изменение настроек запрещены, кроме разрешённого запуска подключения ЭЦП. При отсутствии подключения и данных применяется отдельное пустое состояние по принятым продуктовым правилам.

### Проверка
## REQ-DEC-079
**Применимость:** MVP1

Set Mark отображается в SetCentrum как самостоятельный продуктовый раздел по аналогии с Set Loyalty. На верхнем уровне Set Mark располагаются четыре равноправных раздела в порядке: «Обзор», «Мониторинг маркировки», «Настройки», «Журнал нарушений». Внутри «Мониторинга маркировки» располагаются «Инциденты», «Необходимые действия» и «Аналитика». «Обзор» и «Настройки» не должны быть вложены в Мониторинг, а «Журнал нарушений» должен быть последним пунктом меню Set Mark. Действующая визуализация Журнала отображается непосредственно в SetCentrum без автоматического изменения бизнес-логики Журнала. Функция «Кассы требуют внимания» остаётся в Настройках и группирует данные как «Магазин → Касса → выявленное расхождение или проблема настройки».

## REQ-DEC-077
**Применимость:** MVP1

Если для клиента RU ЭЦП не подключена и данные «Честного знака» ещё не получены, усечённый Обзор не должен показывать нулевые агрегаты как результат мониторинга. Вместо метрик система показывает отдельное пустое состояние «Нет подключения к Честному знаку» и объясняет, что данные недоступны. Пользователю с привилегией подключения ЭЦП доступно действие начала подключения; пользователю без этой привилегии показывается предложение обратиться к администратору. Пустое состояние не раскрывает детали инцидентов.

## REQ-FR-007. Работа без Set Mark в магазинах и при распределённой установке

**Применимость:** MVP1

Для RU-клиента без установленного в магазинах Set Mark после подключения «Честного знака» через ЭЦП в SetCentrum функция централизованно получает отклонения и предоставляет ограниченные «Обзор» и «Аналитику». Для этого режима установка Set Mark в магазинах не требуется. Журнал нарушений, строки и карточки инцидентов, причины, рекомендации и сопоставление с кассовыми данными недоступны.

Если Set Mark установлен в магазинах, в том числе при распределённой схеме, полная детализация формируется по доступным централизованному сервису данным Set Mark и SetRetail. Магазин, данные которого ещё не поступают в SetCentrum, учитывается только по данным «Честного знака»; интерфейс явно показывает неполноту источников и не имитирует наличие недоступной детализации.

### Проверка

Клиент без Set Mark получает агрегаты после подключения ЭЦП без установки продукта в магазинах. Для магазина с доступными данными Set Mark и SetRetail открывается полная детализация; при отсутствии этих данных пользователь видит признак неполноты источников.

## REQ-FR-004. Поиск по штрихкодам, артикулам и кодам маркировки

**Применимость:** MVP1

Список инцидентов поддерживает поиск по штрихкоду, артикулу товара и полному коду маркировки. В одном поле можно указать несколько штрихкодов, артикулов и/или кодов маркировки через запятую. Пробелы вокруг значений игнорируются, значения объединяются по логике «ИЛИ»; для штрихкода, артикула и полного кода маркировки применяется точное совпадение.

### Проверка

Одиночный и смешанный запрос из нескольких значений возвращает объединение соответствующих инцидентов.

## REQ-FR-005. Множественный фильтр магазинов

**Применимость:** MVP1

Пользователь может выбрать один или несколько магазинов. При выборе нескольких магазинов показывается объединённая выборка. Доступны действия «Выбрать все» и «Сбросить». Фильтр совместно применяется с периодом, поиском и остальными фильтрами.

### Проверка

Выбор нескольких магазинов ограничивает список и CSV выбранными магазинами.

## REQ-FR-006. Расширенная выгрузка инцидентов в CSV

**Применимость:** MVP1

CSV формируется по текущей выборке и содержит 23 колонки:

1. ID инцидента.
2. Код правила.
3. Дата и время операции.
4. Магазин.
5. Город.
6. Касса.
7. Штрихкод.
8. Артикул.
9. Наименование товара.
10. Товарная группа.
11. Полный код маркировки.
12. Тип нарушения.
13. Описание исходного отклонения.
14. Результат проверки.
15. Критичность.
16. Риск автоштрафа.
17. Потенциальная сумма штрафа.
18. Установленная причина.
19. Рекомендуемое действие.
20. Контур устранения.
21. Статус анализа.
22. Номер чека или идентификатор операции.
23. Источник проверки.

Текстовые значения экранируются, файл формируется в UTF-8.

### Проверка

CSV содержит все 23 колонки в указанном порядке и только инциденты активной выборки.

Для MVP подтверждены поиск по штрихкоду, артикулу и полному коду маркировки с поддержкой нескольких значений через запятую по логике «ИЛИ» и точным совпадением; множественный фильтр магазинов с действиями «Выбрать все» и «Сбросить»; расширенная CSV-выгрузка текущей выборки из 23 колонок, включая признак риска автоштрафа и потенциальную сумму штрафа; хранение поисковых и экспортных данных товара и операции, необходимых для этих сценариев.

## REQ-DEC-037
**Применимость:** MVP1

Дашборд, список инцидентов, аналитика и необходимые действия используют общий выбранный период.

Дашборд показывает согласованные показатели, топ-5 необходимых действий, разбивку инцидентов по типам, объекты с наибольшим риском и состояние данных. Все значения и разбивки рассчитываются по выбранному периоду и активным фильтрам.

Список инцидентов поддерживает поиск, множественный фильтр по типам нарушений, фильтры критичности и результата. Карточка показывает полный код маркировки и потенциальный штраф.

Потенциальный штраф рассчитывается по точной формуле применимой действующей нормы. Для накопительного состава сумма определяется один раз на нормативный объект и нормативный период; связанные инциденты участвуют в достижении порога, но не умножают один и тот же штраф. При поступлении новых данных сумма пересчитывается по текущему достигнутому порогу.

Технические коды `RA-01`–`RA-05` используются внутри правил анализа, но не показываются пользователю: в списке и карточке отображается понятное наименование результата проверки.

Аналитика пересчитывает показатели и график по активным фильтрам. Период до 14 дней включительно группируется по дням, более длительный период — по неделям.

Клик по показателю, объекту, типу нарушения или колонке графика открывает на вкладке «Инциденты» ровно соответствующую выборку. Для каждого инцидента доступна реальная выгрузка PDF.

## REQ-DEC-010
**Применимость:** MVP1

Для MVP утверждён следующий состав функций:

- система получает отклонения True API и создаёт инциденты;
- система автоматически сопоставляет доступные данные и формирует результат анализа `RA-01`–`RA-05`;
- обзор сети показывает показатели и накопление нарушений по сети, торговым точкам и кассам;
- пользователь может переходить от сети к торговой точке, кассе и инциденту;
- список инцидентов поддерживает фильтрацию и поиск по утверждённым аналитическим разрезам;
- карточка инцидента показывает исходные данные, связанные операции, понятный результат проверки без технического кода `RA-*`, причину, критичность, потенциальный штраф, Контур устранения и рекомендацию;
- аналитика показывает динамику, накопление нарушений и достижение порогов;
- система ежедневно информирует настроенных получателей о критичных нарушениях;
- система формирует CSV по текущим данным и применённым фильтрам;
- Администратор системы может настраивать подключение к True API, получателей уведомлений и срок хранения данных;
- система показывает свежесть данных, состояние источников и ошибки интеграций.

Ручное пользовательское состояние «Новый / Просмотрен» и функция отметки инцидента как просмотренного в MVP не вводятся. У инцидента остаются только системные состояния обработки: `Получен → Анализируется → Анализ завершён / Ошибка обработки`.

Блокирование продаж, автоматическое исправление, назначение ответственных, управление задачами и контроль выполнения в функции MVP не входят.

## Данные, телеметрия, свежесть и полнота

## REQ-DEC-088
**Применимость:** MVP1

Set Agent должен возвращать дату окончания лицензии Set Mark и признак, позволяющий подтвердить полноту истории для состояния «лицензии никогда не было». SetCentrum хранит последнее достоверное состояние лицензии, дату и время его последнего успешного получения и дату окончания, полученную от Set Agent. Значения сохраняются вместе как один версионированный снимок и используются для автономного расчёта состояния. Отсутствие снимка означает «статус неизвестен, достоверной истории нет», а не подтверждённое отсутствие лицензии.

### Проверка
## REQ-DEC-070
**Применимость:** MVP1

Календарный срок хранения данных Мониторинга рассчитывается по дате события в часовом поясе SetCentrum. День события считается первым календарным днём хранения; при сроке 30 дней запись доступна в день события и следующие 29 календарных дней, после чего физически удаляется в начале 31-го календарного дня. Для настроенного меньшего срока применяется та же схема включительного подсчёта.

### Проверка
## REQ-DEC-069
**Применимость:** MVP1

Срок хранения данных Мониторинга составляет 30 календарных дней, если отдельная настройка срока хранения Set Mark отсутствует. Если настройка задана меньше 30 дней, применяется настроенное значение; если она превышает 30 дней, фактический срок ограничивается 30 календарными днями. По окончании фактического срока данные физически удаляются. Удалённые данные не восстанавливаются после покупки или возобновления лицензии; после восстановления доступа пользователь видит только фактически сохранившуюся историю.

### Проверка
## REQ-DEC-068
**Применимость:** MVP1

Для клиента со страной RU после настройки Set Mark и подключения ЭЦП система продолжает получать, обрабатывать и хранить данные Мониторинга независимо от состояния лицензии, в том числе если лицензии никогда не было или льготный период закончился. Лицензионные ограничения управляют пользовательским доступом к функциям и деталям, но сами по себе не останавливают поступление данных. Хранение выполняется в пределах установленного срока хранения.

## REQ-DEC-039
**Применимость:** MVP1

Для инцидента хранится и отображается полный код маркировки; поиск должен находить инцидент по точному полному коду.

Для состояния данных хранятся результат, дата и время последнего обращения за отчётом в «Честный знак», а также состояние связи с Set Centrum.

PDF формируется по данным выбранного инцидента: фиксирует факты, последовательность событий, результат проверки и его обоснование; для допустимого сценария объясняет отсутствие нарушения со стороны ритейлера. В PDF указывается только название организации. Рекомендации, потенциальный штраф, подпись и специальное назначение документа в заголовке не включаются.

## REQ-DEC-018
**Применимость:** MVP1

Для одной торговой сети функция Set Mark должна поддерживать до 25 000 магазинов и до 40 000 касс. Максимальный объём обработки составляет до 100 000 отклонений в сутки; значение рассчитано исходя из 2,5 отклонения на одну кассу при максимальном количестве касс. Инцидент должен появляться в функции не позднее чем через 24 часа после получения соответствующего события Set Mark или «Честным знаком».

Для ручного MVP1 достижимость 24 часов является эксплуатационной обязанностью и требует обязательного запуска синхронизации не реже одного раза в сутки. Системная гарантия SLA требует будущей автоматической периодики с допустимой подписью или авторизацией, доступной Set Mark 24/7.

### Проверка

## REQ-DATA-001. Данные отклонения Честного знака

**Применимость:** MVP1

Система должна получать сведения об отклонениях Честного знака и обязательно сохранять исходные наименования вида и результата из `VIOLATIONS` CSV вместе с полным raw snapshot.

Коды категории, вида и результата заполняются best-effort из версионированного справочника True API. Код может быть `null`, если mapping отсутствует или неоднозначен; такое отклонение сохраняется, ingestion остаётся успешным, а состояние mapping передаётся в последующий анализ как неизвестное значение.

### Проверка

Для импортированного отклонения всегда сохранены raw-наименования, raw snapshot, версия справочника и состояние mapping. При однозначном mapping сохранены коды; unresolved/ambiguous mapping не теряет запись и приводит к обработке неизвестного значения.

## REQ-DATA-003. Срок появления первой статистики

**Применимость:** MVP1

Отсчёт готовности статистики начинается после успешного подключения ЭЦП и получения первого доступного ответа «Честного знака». Первые показатели должны появиться не позднее 24 часов после наступления обоих условий.

При первичном подключении система запрашивает доступную источнику историю, но не более действующего срока хранения — 30 дней. Если источник не предоставляет историю полностью, интерфейс показывает данные с фактической даты начала покрытия и явно указывает неполный период. Полная статистика за 7 или 30 дней появляется после накопления соответствующего периода либо сразу после успешной исторической загрузки.

До получения первых данных интерфейс показывает состояние подключения и загрузки. Отсутствие загруженных данных не отображается как нулевой результат мониторинга.

### Проверка

После успешного подключения и ответа источника первые показатели появляются в пределах 24 часов. Для неполного периода видны дата начала покрытия и состояние загрузки; нулевые показатели не используются вместо отсутствующих данных.
