# Системный контекст и границы реализации

## Контуры системы

Кассовое ПО выполняет проверки в онлайн ЧЗ, ЛМ ЧЗ и Set Mark, затем применяет
действующие правила и принимает решение о продаже. Новый модуль не вмешивается в
этот синхронный путь: он получает уже сформированные события и отклонения для
последующего мониторинга.

Backend Set Mark владеет интеграцией True API, хранением отклонений и инцидентов,
корреляцией и контрактами пользовательского интерфейса. Текущий Журнал нарушений
предоставляет оболочку MVP. SetCentrum используется как источник страны и лицензионного
контекста, но не как место размещения интерфейса.

## Условия запуска

- требуется версия Set Mark, содержащая новую функцию;
- поддерживается старая и новая совместимая версия SetCentrum;
- обновление только SetCentrum при старом Set Mark ничего не показывает;
- для страны, отличной от `RU`, интерфейс, API, фоновые процессы и подключение ЭЦП
  отсутствуют;
- отдельное магазинное оборудование и повышение минимальных требований к кассам не
  требуются;
- центральные мощности определяются инженерным расчётом под целевой профиль нагрузки.

## Лицензия и доступ

Журнал нарушений и Мониторинг используют одну лицензию Set Mark. Действующая лицензия,
лицензионное несоответствие и первые 10 календарных дней после окончания дают полный
доступ MVP. Несоответствие по количеству магазинов или товарной категории показывает
предупреждение, но не ограничивает функции.

Если Set Agent недоступен, состояние рассчитывается по последнему достоверному снимку
и сохранённой дате окончания. Истечение лицензии приоритетнее несоответствия. Изменение
режима применяется при создании новой пользовательской сессии.

Сценарии клиента, у которого лицензии никогда не было, закончился льготный период или
нет достоверной истории, входят в отдельный последующий выпуск усечённого режима и не
должны усложнять архитектуру MVP скрытыми зависимостями.

## Архитектурные ограничения

- производственный стек выбирает команда разработки;
- реальные ЭЦП, клиентские данные и секреты не попадают в Git;
- внешние интеграции вызываются асинхронно относительно кассовой продажи;
- сбой мониторинга не должен блокировать кассовый процесс;
- публичные контракты версионируются и поддерживают повторную доставку;
- решение о центральном компоненте будущего режима без Set Mark остаётся открытым и
  не является зависимостью MVP.
