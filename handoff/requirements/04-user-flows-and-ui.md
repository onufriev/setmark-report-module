# Пользователи, сценарии и интерфейс

Этот документ собран из канонического каталога `requirements/`. Он предназначен для чтения командой реализации и не заменяет канонические требования.

## MVP

### REQ-DEC-186. Сопровождение подключения в MVP

В MVP отдельный администратор и новая ролевая модель не вводятся. Любой пользователь с доступом к текущему Журналу нарушений может повторно авторизоваться в True API, исправлять подключение, запускать ручную синхронизацию, контролировать свежесть данных и настраивать критичность видов отклонений. Система должна показывать состояние подключения, свежесть данных и понятную причину ошибки. Назначение конкретного ответственного сотрудника является организационным решением клиента и не контролируется продуктом.


**Как проверить**
Реализация соответствует решению PM-DEC-201.

### REQ-DEC-144. Решение Product Manager

В MVP любой пользователь текущего Журнала нарушений без дополнительных ролей и привилегий может использовать Обзор, Инциденты, карточку источников и настройки подключения True API, критичности и ручной синхронизации. Рекомендации в MVP не формируются и не отображаются; права для функций следующего этапа определяются при их реализации.


**Как проверить**
Реализация соответствует решению PM-DEC-159.

### REQ-DEC-118. Решение Product Manager

В текущем Журнале нарушений нет ролевой модели. В MVP настройку подключения True API может выполнить любой пользователь, имеющий доступ к Журналу нарушений; отдельная административная роль или привилегия для этой операции не требуется.


**Как проверить**
Реализация соответствует решению PM-DEC-133.

### REQ-DEC-112. Решение Product Manager

**Как проверить**
Реализация соответствует решению PM-DEC-127.

### REQ-DEC-011. Источник интерфейса и компонентов

Основным источником компонентов для новых экранов Мониторинга маркировки является корпоративная библиотека `@crystalservice/csi_ui` версии `1.30.3`. Актуальный frontend Set Mark в `application/ui/modules/frontend` используется как источник действующей визуализации Журнала нарушений и референс существующих сценариев. Устаревший frontend в `application/setmark/modules/web-frontend` может использоваться только как дополнительный источник реализованных сценариев, но не как дизайн-основа.

Для визуального прототипа MVP разрешено переиспользовать подтверждённые компоненты библиотеки и паттерны текущего Журнала нарушений, включая верхнюю панель, breadcrumbs, таблицы, фильтры, пагинацию, диалоги, статусные метки, индикаторы загрузки и пустые состояния. Каркас приложения и продуктовая навигация SetCentrum не моделируются в MVP.

Исходники `@crystalservice/csi_ui` в переданном снимке приложения отсутствуют. Для визуального прототипа допустимо воспроизвести наблюдаемые правила использования компонентов. Для сборки рабочего интерфейса необходим доступ к корпоративному npm-реестру.

Изменение библиотечных компонентов и создание отсутствующих компонентов этим решением не разрешены и требуют отдельного решения Product Manager. Отсутствующие компоненты должны быть зафиксированы как ограничение и влияние на прототип.


**Как проверить**

Визуальный прототип использует зарегистрированные источники в установленных границах и не выдаёт существующее приложение или библиотеку компонентов за готовый прототип.

### REQ-DEC-104. Доступ демонстрационного режима без Set Mark

На следующем этапе раздел Set Mark должен быть виден RU-пользователю SetCentrum независимо от наличия установленного Set Mark или лицензии. Право просмотра Журнала остаётся базовым допуском к данным. При отсутствии полного доступа пользователь видит агрегаты Честного знака в Обзоре и Аналитике, но не видит строки и идентификаторы закрытых объектов; администратору с необходимой привилегией доступна точка начала подключения ЭЦП, остальные настройки заблокированы.


**Как проверить**
Без установленного Set Mark пользователь получает только разрешённый демонстрационный доступ; отсутствие базового права не раскрывает данные, а подключение ЭЦП доступно только администратору с соответствующей привилегией.

При наличии базового права каждая операция дополнительно проверяет соответствующую отдельную привилегию Set Mark, включая просмотр обзора и аналитики, просмотр деталей инцидента, поиск и фильтрацию, экспорт, уведомления и изменение настроек. ### REQ-DEC-008. Решение Product Manager

В Set Mark первичны отдельные привилегии, а не строго зафиксированные роли. Роль представляет собой изменяемый набор привилегий. Управление ролями, назначение и исключение привилегий выполняются существующими средствами Set Centrum; отдельный инструмент управления ролями и привилегиями для новой функции не создаётся.

Для следующего этапа зафиксирован следующий каталог привилегий:

- просмотр общего обзора и аналитики по нарушениям;
- просмотр списка и карточки инцидентов, включая исходные данные, объяснение результата анализа, риски и рекомендации;
- фильтрация и поиск инцидентов;
- выгрузка доступных данных в CSV;
- получение настроенных уведомлений о критичных нарушениях;
- настройка подключения к True API;
- настройка получателей уведомлений;
- настройка срока хранения данных.

Пользователь функции — любой сотрудник, ответственный за разбор нарушений маркировки. В крупной сети это может быть специализированный аналитик или сотрудник службы маркировки; в небольшой компании — владелец, руководитель, товаровед или администратор. Продукт не требует создания отдельной должности.

Необязательные профили ролей по умолчанию:

- профиль «Аналитик по работе с маркировкой» получает первые пять рабочих привилегий, связанных с просмотром, анализом, выгрузкой и получением уведомлений;
- «Администратор системы» получает весь каталог привилегий, включая три административные настройки.

Использование профиля «Аналитик по работе с маркировкой» не обязательно. Состав обеих ролей по умолчанию может быть изменён в Set Centrum. Все привилегии на просмотр, анализ и выгрузку действуют только в пределах сетей и торговых точек, доступных пользователю согласно настройкам Set Centrum. Получатель уведомлений не является отдельной ролью. Назначение ответственных, управление задачами и контроль исправления в MVP не вводятся. Способ аутентификации и техническая интеграция с существующей моделью доступа определяются отдельно.


**Как проверить**
Реализация соответствует решениям PM-DEC-008, PM-DEC-010 и PM-DEC-019.

В автономном прототипе следующего этапа пункты вне Set Mark могут быть безопасными заглушками, сохраняющими визуальный контекст меню.

### REQ-DEC-042. Решение Product Manager

Вместо одного линейного пользовательского пути для аналитика зафиксированы два основных пути. Структура путей уточнена Product Manager 27.08.2026.

### Путь 1. Критический контроль

1. Пользователь входит в Set Mark через существующий механизм аутентификации и открывает раздел мониторинга нарушений маркировки.
2. Выбирает период либо использует период по умолчанию «Неделя».
3. Сразу проверяет, есть ли критические инциденты, для которых возможен автоматический штраф.
4. Если критические инциденты есть, пользователь рассматривает их в первую очередь и изучает необходимые действия, предотвращающие повторение таких инцидентов.
5. При необходимости пользователь переходит к связанным инцидентам и карточке инцидента, чтобы понять исходные факты, причину, результат проверки, критичность, Контур устранения и рекомендацию.
6. После определения необходимого действия пользователь переходит к внесению изменений в соответствующем Контуре устранения. Выполнение изменения и контроль результата происходят вне функции.

### Путь 2. Регулярное снижение количества нарушений

1. Если критических инцидентов нет, пользователь оценивает необходимые действия для снижения общего количества нарушений.
2. Пользователь выбирает в первую очередь действия, с которыми связано наибольшее количество инцидентов, чтобы получить максимальный эффект от внесённых изменений.
3. При необходимости переходит от действия к связанным инцидентам, уточняет причины поиском, фильтрами, карточками и аналитикой.
4. Цель регулярного пути — уменьшать количество нарушений и связанный с ними регуляторный риск, в том числе риск последующих проверок и штрафов через индикаторы риска «Честного знака».
5. После выбора действия пользователь вносит изменения в соответствующем Контуре устранения вне функции.

В обоих путях пользователь может использовать кликабельные агрегаты Дашборда, список инцидентов, карточку, аналитику, CSV и PDF как средства детализации и подтверждения принятого решения. Переход из любого агрегата должен открывать ровно соответствующую выборку инцидентов.


**Как проверить**

Пользователь без дополнительных объяснений понимает, что при наличии критических инцидентов сначала должен работать с ними и их необходимыми действиями, а при отсутствии критических инцидентов — выбирать действия с наибольшим количеством связанных инцидентов.

### REQ-DEC-024. Решение Product Manager

Для MVP основной пользовательский сценарий аналитика внутри Set Mark строится вокруг двух приоритетов, уточнённых Product Manager 27.08.2026:

- **сначала критический риск:** на Дашборде пользователь сразу видит наличие критических инцидентов и связанные с ними необходимые действия; при наличии таких инцидентов они имеют безусловный приоритет;
- **затем регулярное снижение нарушений:** если критических инцидентов нет, пользователь выбирает необходимые действия по количеству связанных инцидентов и работает на уменьшение общего количества нарушений.

Для детализации пользователь может выбрать магазин, кассу, товарную группу либо тип нарушения и перейти к соответствующему списку инцидентов; уточнить выборку поиском и фильтрами; открыть карточку инцидента; изучить исходные данные, понятный результат проверки без технического кода `RA-*`, объяснение, критичность, потенциальный штраф, Контур устранения и рекомендацию; вернуться к списку или аналитике с сохранением выбранного контекста; при необходимости выгрузить текущую выборку в CSV или сформировать PDF выбранного инцидента.

Дополнительные точки входа: из ежедневного email-дайджеста пользователь переходит в Set Mark к списку Инцидентов за предыдущий календарный день с фильтром новых критичных отклонений и контекстом организации; администратор открывает настройки функции для управления подключением, получателями уведомлений и сроком хранения данных; при недостаточных правах, неполных или устаревших данных интерфейс показывает доступный результат и понятное ограничение.


**Как проверить**

Реализация не заставляет пользователя проходить всю аналитику последовательно: критический путь доступен сразу, а регулярный путь выводит на действия с наибольшим влиянием на количество нарушений.

### REQ-DEC-175. Решение Product Manager

На следующем этапе настроенный получатель получает один утренний email-дайджест, оценивает количество и распределение новых критичных отклонений за предыдущий день и переходит по ссылке к отфильтрованному списку Инцидентов для разбора. При отсутствии новых критичных отклонений действий пользователя не требуется и письмо не отправляется.


**Как проверить**
Реализация соответствует решению PM-DEC-190.

### REQ-DEC-041. Решение Product Manager

Для целевого пользователя зафиксированы два основных бизнес-сценария, которые различаются по приоритету. Сценарии уточнены Product Manager 27.08.2026.

### Критический сценарий

Пользователь заходит в функцию прежде всего для проверки, появились ли критические инциденты, для которых возможен автоматический штраф. Если такие инциденты есть, они имеют безусловный приоритет над остальной аналитикой.

Пользователь сразу изучает критические инциденты и необходимые действия, которые должны устранить причину и предотвратить повторение. После этого фактическое внесение изменений выполняется в соответствующем Контуре устранения вне функции.

### Регулярный сценарий

Если критических инцидентов нет, пользователь работает на снижение общего количества нарушений, чтобы уменьшать регуляторный риск, в том числе риск последующих проверок и штрафов через индикаторы риска «Честного знака».

В этом режиме пользователь выбирает необходимые действия, способные предотвратить наибольшее количество инцидентов. Действия сортируются по количеству связанных инцидентов в соответствии с правилом приоритизации; пользователь при необходимости переходит к связанным инцидентам для уточнения причин.

На Дашборде доступен топ-5 действий, на отдельной вкладке — полный список. Выполнение действий и контроль результата происходят вне системы.

Пользователь при необходимости формирует PDF-описание любого выбранного инцидента.


**Как проверить**

Интерфейс и порядок действий позволяют без дополнительных объяснений пройти оба сценария: сначала обнаружить и разобрать критические инциденты, а при их отсутствии — выбрать действия с наибольшим ожидаемым влиянием на количество нарушений.

### REQ-DEC-023. Решение Product Manager

На следующем этапе функция внутри Set Mark должна поддерживать следующие бизнес-сценарии:

- **критический контроль:** аналитик проверяет наличие критических инцидентов, для которых возможен автоштраф, изучает их причины и необходимые действия и переходит к внесению изменений в соответствующем Контуре устранения;
- **регулярное снижение нарушений:** при отсутствии критических инцидентов аналитик выбирает действия, предотвращающие наибольшее количество инцидентов, чтобы снижать общее количество нарушений и связанный с ними регуляторный риск;
- аналитик переходит к отдельному инциденту и изучает исходные данные, понятный результат проверки без технического кода `RA-*`, критичность, потенциальный штраф, Контур устранения и рекомендацию;
- аналитик использует фильтры и аналитику, чтобы исследовать динамику, повторяющиеся нарушения и связанные с выбранным действием инциденты;
- пользователь выгружает выбранные данные в CSV для дополнительного анализа и отчётности;
- настроенные получатели получают один ежедневный email-дайджест о новых критичных отклонениях за предыдущий день и переходят к соответствующей отфильтрованной выборке Инцидентов;
- администратор системы настраивает подключение, получателей уведомлений и срок хранения данных;
- при неполных или устаревших данных пользователь видит их состояние и ограничения, чтобы не принять ошибочное решение.

Назначение ответственных, постановка задач и контроль устранения нарушений не входят в данный этап.


**Как проверить**

Реализация поддерживает оба основных режима работы: безусловный приоритет критических инцидентов и регулярную приоритизацию действий по количеству предотвращаемых инцидентов.

## Формат описания каждого сценария

- роль;
- исходная ситуация и предусловия;
- действие или последовательность действий;
- ожидаемый результат и бизнес-эффект;
- исключения и ошибки;
- зависимые сущности, настройки, оборудование и интеграции.

Нужно покрыть основные, редкие и критичные сценарии. При необходимости сценарии разделяются по ролям или процессам.
