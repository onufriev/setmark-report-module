# Возможности и приёмка

Этот документ собран из канонического каталога `requirements/`. Он предназначен для чтения командой реализации и не заменяет канонические требования.

## MVP

### REQ-DEC-147. Решение Product Manager

Если Set Mark установлен или обновлён до версии, содержащей Мониторинг маркировки MVP, новые экраны появляются в интерфейсе текущего Журнала нарушений независимо от версии SetCentrum. При старой версии Set Mark новая функциональность отсутствует без заглушки, даже если SetCentrum обновлён.


**Как проверить**
Реализация соответствует решению PM-DEC-162.

### REQ-DEC-130. Решение Product Manager

В MVP пользователь работает с неизменёнными функциями текущего Журнала нарушений, Обзором, списком Инциденты, карточкой собранных и сопоставленных данных и настройками True API, критичности и ручной синхронизации. Карточка не содержит результата автоматического анализа и рекомендаций. CSV, PDF, отдельные Необходимые действия, Аналитика и ежедневные уведомления относятся к следующему этапу.


**Как проверить**
Реализация соответствует решению PM-DEC-145.

### REQ-DEC-119. Решение Product Manager

До настройки True API пользователь может открыть Мониторинг в текущем интерфейсе Журнала нарушений, но вместо показателей видит состояние «Подключение к Честному знаку не настроено» и действие начала настройки. Существующая функциональность Журнала нарушений продолжает работать независимо от состояния подключения True API.


**Как проверить**
Реализация соответствует решению PM-DEC-134.

### REQ-DEC-111. Решение Product Manager

Все пользовательские экраны MVP Мониторинга маркировки открываются и работают в интерфейсе текущего Журнала нарушений. Отдельный раздел Set Mark и новая продуктовая навигация внутри SetCentrum в MVP не создаются.


**Как проверить**
Реализация соответствует решению PM-DEC-126.

### REQ-DEC-090. Решение Product Manager

Одно поле выполняет точный поиск по одному или нескольким штрихкодам, артикулам и полным кодам маркировки через запятую по логике «ИЛИ»; фильтр позволяет выбрать несколько магазинов, выбрать все или сбросить выбор и объединяется с другими группами фильтров по логике «И». Требования к CSV применяются на следующем этапе.


**Как проверить**
Реализация соответствует решению PM-DEC-093.

### REQ-FR-007. Работа без Set Mark в магазинах и при распределённой установке

Если Set Mark установлен в магазинах, в том числе при распределённой схеме, полная детализация формируется по доступным централизованному сервису данным Set Mark и SetRetail. Магазин, данные которого ещё не поступают в SetCentrum, учитывается только по данным «Честного знака»; интерфейс явно показывает неполноту источников и не имитирует наличие недоступной детализации.


**Как проверить**

Для магазина с доступными данными Set Mark и SetRetail открывается полная детализация; при отсутствии части данных пользователь видит признак неполноты источников.

### REQ-FR-004. Поиск по штрихкодам, артикулам и кодам маркировки

Список инцидентов поддерживает поиск по штрихкоду, артикулу товара и полному коду маркировки. В одном поле можно указать несколько штрихкодов, артикулов и/или кодов маркировки через запятую. Пробелы вокруг значений игнорируются, значения объединяются по логике «ИЛИ»; для штрихкода, артикула и полного кода маркировки применяется точное совпадение.


**Как проверить**

Одиночный и смешанный запрос из нескольких значений возвращает объединение соответствующих инцидентов.

### REQ-FR-005. Множественный фильтр магазинов

Пользователь может выбрать один или несколько магазинов. При выборе нескольких магазинов показывается объединённая выборка. Доступны действия «Выбрать все» и «Сбросить». Фильтр совместно применяется с периодом, поиском и остальными фильтрами.


**Как проверить**

Выбор нескольких магазинов ограничивает список выбранными магазинами. На следующем этапе тот же фильтр применяется к CSV.

### REQ-DEC-051. Поиск, фильтр магазинов и расширенная выгрузка

Для MVP подтверждены поиск по штрихкоду, артикулу и полному коду маркировки с поддержкой нескольких значений через запятую по логике «ИЛИ» и точным совпадением, а также множественный фильтр магазинов с действиями «Выбрать все» и «Сбросить». Расширенная CSV-выгрузка текущей выборки относится к следующему этапу.


**Как проверить**

MVP соответствует REQ-FR-004 и REQ-FR-005; REQ-FR-006 проверяется на следующем этапе.

### REQ-DEC-037. Решение Product Manager

Обзор и список инцидентов используют общий выбранный период.

Обзор показывает основные агрегаты, распределение отклонений и состояние данных. Все значения и разбивки рассчитываются по выбранному периоду и активным фильтрам.

Список инцидентов поддерживает поиск, группировки, множественный фильтр по типам отклонений и фильтр критичности. Карточка показывает полный код маркировки и сопоставленные данные источников.

Клик по показателю, объекту или типу отклонения открывает в списке «Инциденты» соответствующую выборку. Потенциальный штраф, результаты `RA-01`–`RA-05`, отдельная Аналитика, Необходимые действия и PDF относятся к следующему этапу.


**Как проверить**
Реализация соответствует решениям PM-DEC-038, PM-DEC-054, PM-DEC-055 и PM-DEC-056.

### REQ-DEC-010. Решение Product Manager

Для MVP утверждён следующий состав функций:

- система получает отклонения True API и создаёт инциденты;
- система автоматически сопоставляет доступные данные источников без формирования результата анализа `RA-01`–`RA-05`;
- Обзор показывает основные агрегаты и распределение отклонений по сети, торговым точкам и кассам;
- пользователь может переходить от сети к торговой точке, кассе и инциденту;
- список инцидентов поддерживает фильтрацию и поиск по утверждённым аналитическим разрезам;
- карточка инцидента показывает данные Честного знака, Журнала нарушений, чека, проверок и настроек;
- пользователь может настраивать критичность видов отклонений;
- любой пользователь текущего Журнала нарушений может настраивать подключение к True API; ролевая модель и отдельная административная привилегия для этой операции в MVP отсутствуют;
- система показывает свежесть данных, состояние источников и ошибки интеграций.

Результаты анализа, рекомендации, CSV, PDF, отдельные разделы «Необходимые действия» и «Аналитика» и ежедневные уведомления относятся к следующему этапу.

Блокирование продаж, автоматическое исправление, назначение ответственных, управление задачами и контроль выполнения в функции MVP не входят.


**Как проверить**
Реализация соответствует решению PM-DEC-010.

### REQ-FR-001. Централизованный мониторинг

Система должна агрегированно отображать нарушения по сети магазинов, торговым точкам, кассам, товарным категориям и типам ошибок.


**Как проверить**

Пользователь может перейти от обзора сети к данным по указанным измерениям.

### REQ-DEC-033. Готовые и произвольный диапазоны дат

В MVP Обзор и Инциденты используют единый явно выбранный период. Доступны готовые диапазоны «Сегодня», «7 дней», «30 дней» и вариант «Произвольный» в пределах фактического срока хранения. При первом открытии применяются последние 7 календарных дней, включая текущий день, в часовом поясе SetCentrum. Выбранный период сохраняется при переходе между Обзором, списком и карточкой. На следующем этапе тот же период применяется к Аналитике, необходимым действиям и выгрузкам.


**Как проверить**

В Обзоре, списке и карточке значения соответствуют одному выбранному периоду. По умолчанию выбраны последние 7 календарных дней с текущим днём. Произвольный диапазон не выходит за пределы сохранившихся данных, период виден пользователю и сохраняется между переходами.

### REQ-DEC-183. Решение Product Manager

Нагрузочная приёмка MVP подтверждает профиль 25 000 магазинов, 40 000 касс и 100 000 отклонений в сутки; открытие Обзора, списка и карточки не более чем за 3 секунды для 95% запросов; рост времени кассовой операции не более 5% и 50 мс; рост доли ошибок не более 0,1 процентного пункта; отсутствие потери и дублирования событий; замедление только Мониторинга при перегрузке и последующую обработку очереди после восстановления.


**Как проверить**
Реализация соответствует решению PM-DEC-198.

### REQ-DEC-151. Решение Product Manager

Приёмка MVP подтверждает две комбинации: версия Set Mark с новой функциональностью предоставляет её в текущем Журнале нарушений при поддерживаемой старой или новой версии SetCentrum; старая версия Set Mark не показывает новую функциональность и заглушку после обновления только SetCentrum. В обеих комбинациях существующие функции Журнала нарушений сохраняются.


**Как проверить**
Реализация соответствует решению PM-DEC-166.

### REQ-DEC-135. Решение Product Manager

MVP принимается при сохранении текущих функций Журнала нарушений и работоспособности Обзора, списка Инциденты с поиском, фильтрами и группировками, карточки с данными ЧЗ, ЖН, чека, проверок и настроек, а также настроек True API, критичности и ручной синхронизации. Результаты анализа, рекомендации, CSV, PDF, отдельные разделы Необходимые действия и Аналитика и ежедневные уведомления не являются критериями приёмки MVP.


**Как проверить**
Реализация соответствует решению PM-DEC-150.

### REQ-DEC-128. Решение Product Manager

В MVP настройка подключения и ручной запуск True API доступны при действующей лицензии, лицензионном несоответствии и в течение 10-дневного льготного периода. Для этих операций состояния несоответствия и льготного периода не создают дополнительного предупреждения или ограничения. После окончания льготного периода, при подтверждённом состоянии «лицензии никогда не было» и при неизвестном статусе без достоверной истории настройка и запуск недоступны. При недоступности Set Agent доступ рассчитывается по последнему достоверному сохранённому состоянию и дате окончания. Получение данных без лицензионного доступа относится к следующему этапу.


**Как проверить**
Реализация соответствует решению PM-DEC-143.

### REQ-DEC-124. Решение Product Manager

Приёмка состояний синхронизации проверяет отсутствие первой загрузки, выполнение без параллельного повторного запуска, успешный результат с отклонениями, успешный пустой ответ, ошибку без кнопки «Повторить», устаревшие данные и состояние «Данные получены не по всем ИНН». Состояния «история доступна с даты» и «недостаточно данных для анализа» не обозначаются как частичная загрузка.


**Как проверить**
Реализация соответствует решению PM-DEC-139.

### REQ-DEC-122. Решение Product Manager

Приёмка первичной настройки подтверждает, что любой пользователь текущего Журнала нарушений может настроить подключение отдельно для выбранного ИНН; успешная авторизация с УКЭП и проверка соединения переводят подключение в настроенное состояние, в том числе при корректном пустом ответе True API; до настройки Мониторинг показывает специальное состояние, а Журнал нарушений остаётся работоспособным.


**Как проверить**
Реализация соответствует решению PM-DEC-137.

### REQ-DEC-117. Решение Product Manager

MVP принимается в интерфейсе текущего Журнала нарушений. Наличие отдельного раздела Set Mark, продуктовой навигации или встроенной визуализации в SetCentrum не является критерием приёмки MVP.


**Как проверить**
Реализация соответствует решению PM-DEC-132.

### REQ-DEC-086. Решение Product Manager

Приёмка MVP должна покрывать работу новой функциональности для любого пользователя текущего интерфейса Журнала нарушений, без отдельной визуализации в SetCentrum и без дополнительной ролевой модели; `RU` и корректную страну не `RU`; действующую лицензию, лицензионное несоответствие по количеству и категории и 10-дневный льготный период. Проверяется, что полный режим открывает функции Журнала, а частичное лицензирование и несовпадение категории дают только предупреждение. Для не `RU` Мониторинг, его API, процессы и ЭЦП отсутствуют. При недоступности Set Agent состояние пересчитывается по сохранённой дате окончания. Срок хранения не превышает 30 дней, удалённые данные не восстанавливаются. Отдельно выполняются сценарии первичной настройки True API, точного массового поиска и множественного выбора магазинов. CSV проверяется на следующем этапе.

Приёмка завершённого льготного периода, подтверждённого отсутствия лицензии, неизвестного статуса без истории, усечённого Обзора и лицензионных заглушек выполняется на следующем этапе по REQ-DEC-108.


**Как проверить**
Реализация соответствует решению PM-DEC-089.

### REQ-AC-001. Поиск и фильтр магазинов

Приёмка подтверждает:

1. Поиск по одному штрихкоду, одному артикулу и одному полному коду маркировки находит соответствующие инциденты.
2. Смешанные значения через запятую объединяются по логике «ИЛИ», пробелы игнорируются.
3. Можно выбрать несколько магазинов, выбрать все и сбросить выбор.
4. Фильтр магазинов совместно работает с периодом, поиском и остальными фильтрами.
5. CSV не является частью приёмки MVP и проверяется на следующем этапе.


**Как проверить**

Сценарии выполняются на данных минимум двух магазинов, двух штрихкодов, двух артикулов и двух полных кодов маркировки.

### REQ-DEC-043. Решение Product Manager

Приёмка дополнительно должна подтвердить:

1. Период и фильтры одинаково применяются на связанных экранах.
2. Число в кликабельном агрегате совпадает с числом открытых по нему инцидентов.
3. Каждый инцидент имеет один тип нарушения и не учитывается в разбивке дважды.
4. Критичные виды отклонений визуально выделены и показываются раньше некритичных.
5. Поиск находит инцидент по полному коду маркировки.
6. Блок состояния данных содержит согласованные сигналы синхронизации.
7. Распределение по видам отклонений учитывает выбранный период и активные фильтры Обзора; сумма его значений совпадает с общим числом инцидентов текущей выборки.
8. Аналитика, необходимые действия, PDF и потенциальный штраф не входят в приёмку MVP.


**Как проверить**
Реализация соответствует составу сокращённого MVP; отложенные функции не показываются как готовые.

### REQ-DEC-025. Решение Product Manager

Для MVP функция считается соответствующей требованиям, если:

1. Пользователь открывает новую функциональность в текущем интерфейсе Журнала нарушений.
2. Обзор показывает период, состояние данных, основные агрегаты и распределение отклонений.
3. Фильтры позволяют перейти от сети, магазина, кассы, товарной группы или вида нарушения к соответствующим инцидентам.
4. Для одного отклонения создаётся один инцидент с исходным снимком и сопоставленными данными.
5. Карточка показывает данные ЧЗ, ЖН, чека, проверок и настроек без результата анализа и рекомендации.
6. Пользователь может настроить подключение True API, критичность видов отклонений и вручную запустить синхронизацию.
7. Устаревшие, неполные и неизвестные данные обрабатываются согласно утверждённым исключительным сценариям без присвоения RA-01–RA-05.
8. Обзор, список и карточка открываются не более чем за 3 секунды для 95% запросов. Появление инцидента не позднее 24 часов остаётся целевым SLA при ручном запуске синхронизации.
9. Повторная доставка не создаёт дубликатов; после сбоя обработка автоматически продолжается без потери исходных отклонений.
10. Результаты анализа, рекомендации, CSV, PDF, необходимые действия, Аналитика и уведомления отсутствуют в MVP.


**Как проверить**
Реализация соответствует решениям PM-DEC-025, PM-DEC-089 и PM-DEC-112.

### REQ-DEC-140. Решение Product Manager

Проверка MVP успешна, если пользователь без дополнительных объяснений может открыть Обзор, определить количество и распределение отклонений, увидеть критичные виды раньше некритичных, перейти к соответствующей выборке Инцидентов, применить поиск, фильтры и группировки и открыть карточку с данными ЧЗ, ЖН, чека, проверок и настроек. Результат анализа, рекомендации, CSV, PDF, отдельные Необходимые действия, Аналитика и уведомления в проверку MVP не входят.


**Как проверить**
Реализация соответствует решению PM-DEC-155.

## Следующий этап

### REQ-DEC-169. Решение Product Manager

На следующем этапе система один раз в сутки в 09:00 по часовому поясу SetCentrum формирует для организации email-дайджест о новых критичных отклонениях за предыдущий календарный день. Получатели задаются в настройках Set Mark. Ссылка из письма открывает Инциденты с соответствующими периодом и фильтрами. В усечённом режиме уведомления недоступны.

### REQ-DEC-044. Решение Product Manager

Проверка прототипа считается успешной, если пользователь без дополнительных объяснений может пройти оба основных пути. Формат проверки уточнён Product Manager 27.08.2026.

### Критический путь

1. Выбрать период.
2. Сразу определить, есть ли критические инциденты, для которых возможен автоматический штраф.
3. При наличии таких инцидентов увидеть их как главный приоритет.
4. Понять, какие необходимые действия связаны с критическими инцидентами, и при необходимости перейти к подтверждающим инцидентам и их карточкам.
5. Понять, в каком Контуре устранения нужно внести изменение.

### Регулярный путь

1. При отсутствии критических инцидентов перейти к снижению общего количества нарушений.
2. Увидеть необходимые действия, отсортированные так, чтобы действия с наибольшим количеством связанных инцидентов были очевидным приоритетом.
3. Понять, какие инциденты составляют выбранное действие, и при необходимости исследовать их через фильтры, карточки и аналитику.
4. Понять, какое изменение нужно внести вне функции для предотвращения максимального количества повторных инцидентов.

В обоих путях пользователь также должен уметь перейти из кликабельного агрегата к совпадающей выборке инцидентов, применить фильтры аналитики, увидеть пересчёт показателей и при необходимости сформировать PDF выбранного инцидента.


**Как проверить**

Пользователь без подсказки выбирает правильный приоритет: критические инциденты — всегда первыми; при их отсутствии — действия с максимальным количеством связанных инцидентов.

### REQ-DEC-026. Решение Product Manager

Идея считается подтверждённой, если представитель целевого пользователя на демонстрационных данных без дополнительных объяснений сможет выполнить сценарии, уточнённые Product Manager 27.08.2026:

1. При наличии критических инцидентов сразу обнаружить их и перейти к необходимым действиям, не тратя время на полный последовательный анализ остальных данных.
2. По карточке критического или выбранного инцидента понять, что произошло, почему получен результат проверки, насколько нарушение критично и к какому Контуру устранения относится, не интерпретируя технические коды `RA-*`.
3. При отсутствии критических инцидентов определить действие, способное предотвратить наибольшее количество инцидентов, и понять связанные с ним причины.
4. Понять рекомендуемое следующее действие и перейти к соответствующему Контуру устранения вне функции.
5. Увидеть ограничения при неполных или устаревших данных и не принять их за достоверный полный результат.
6. При необходимости использовать аналитику, CSV и PDF как инструменты детализации и подтверждения решения.
7. Подтвердить, что функция помогает снижать риск штрафов двумя способами: быстро реагировать на критические инциденты и регулярно уменьшать общее количество нарушений.


**Как проверить**

Демонстрационные данные должны содержать как минимум один сценарий с критическим инцидентом и один сценарий без критических инцидентов, но с несколькими необходимыми действиями разного масштаба.
