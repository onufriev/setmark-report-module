# Product Compiler

Сразу прочитай `PRODUCT-COMPILER.md`.

Нельзя придумывать требования, пропускать области, редактировать `project-state.json`, принимать найденный UI автоматически, создавать прототип до разрешённого этапа или формировать отчёты вне `reports/`.

Перед визуальным прототипом:

1. закрой все области gate `VISUAL_PROTOTYPE`;
2. зафиксируй требования через `tools/commit_requirements.py`;
3. создай и утверди отчёт PRODUCT_DEFINITION.

Перед рабочим прототипом отдельно подтверди стек и источник данных. Сразу подготовь `prototype-manifest.json` и полный `PROTOTYPE-RUNBOOK.md`.

Отчёт завершай только через `tools/finalize_phase_review.py`. После показа остановись и жди отдельного подтверждения Product Manager.
## Изменения в уже пройденном процессе

Сообщение Product Manager вида «Я изменил требования/библиотеку компонентов/прототип, перезапусти процесс» является исполняемой командой. Сам прочитай `internal/restart-process.md`, классифицируй изменение, выполни impact analysis и продолжи с первого затронутого этапа. Не выдавай Product Manager Python-команды и не начинай процесс заново без необходимости.


## Версионирование

Версию продукта бери только из `VERSION`, а версию JSON-контракта — только из `schemas/schema-version.schema.json`. Не дублируй номера версий в коде, схемах, тестах и документации. Подробнее: `internal/versioning.md`.

## Critic agents

Доступны специализированные критики из `critics/agents/`, но их использование полностью опционально.

Перед завершением значимого этапа один раз спроси Product Manager, хочет ли он подключить критика для дополнительной проверки. При согласии предложи только релевантных критиков по `critics/PROCESS-INTEGRATION.md` и запускай исключительно выбранных. При отказе продолжай обычный процесс: отсутствие critic report не блокирует этап и не должно отражаться как риск.
