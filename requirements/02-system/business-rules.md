## REQ-DEC-085. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-088
**Применимость:** MVP1

Доступность вычисляется в едином порядке для UI, API и фоновых процессов: 1) нормализовать `setmark.country`; 2) применить ограничение страны, полностью исключив Мониторинг для не `RU`; 3) проверить базовое право просмотра Журнала; 4) определить состояние лицензии по текущим данным и достоверной истории; 5) применить приоритет истечения лицензии над лицензионным несоответствием; 6) выбрать полный или ограниченный набор функций; 7) перед каждой операцией дополнительно проверить требуемую функциональную или административную привилегию. Одинаковые входные данные должны приводить к одинаковому результату во всех каналах.

## REQ-DEC-082. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-085
**Применимость:** MVP1

Журнал нарушений и Мониторинг маркировки используют одну общую лицензию Set Mark; отдельные лицензии для этих функций или демонстрационного режима не вводятся. Отдельного типа «пробная лицензия» нет: обычная лицензия с ограниченным сроком считается действующей до даты окончания, после чего применяются общий льготный период и ограничения. Лицензионное несоответствие возможно только при наличии хотя бы одной действующей лицензии и включает недостаточное количество лицензий или неподходящую товарную категорию. Ноль действующих лицензий не является несоответствием: состояние определяется как льготный период, завершённый льготный период, «лицензии никогда не было» либо неизвестное состояние согласно достоверной истории. Истечение лицензии имеет приоритет над признаком лицензионного несоответствия.

Реализация соответствует решению PM-DEC-085.

## REQ-DEC-053. Расчёт потенциального штрафа

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-055, PM-DEC-056, PM-DEC-104
**Применимость:** MVP1

Потенциальный штраф рассчитывается по точной формуле применимой нормы КоАП, действующей на дату кассовой операции. Значение отражает возможный финансовый риск и не означает, что штраф фактически назначен.

На Обзоре показатель агрегируется только по инцидентам выбранного пользовательского периода и подписывается как расчётная оценка за этот период, а не прогноз или сумма уже назначенного штрафа.

- Если норма устанавливает фиксированную ставку за единицу нарушения, потенциальный штраф рассчитывается как ставка, умноженная на количество единиц, к которым применяется состав.
- Если размер санкции зависит от накопленного количества нарушений за нормативный период, штраф рассчитывается один раз на соответствующий нормативный объект и период. Связанные инциденты участвуют в определении достигнутого порога, но один и тот же штраф не суммируется по каждому инциденту.
- При поступлении новых инцидентов в незавершённом нормативном периоде текущий потенциальный штраф пересчитывается по фактически достигнутому порогу.
- Агрегированный потенциальный штраф на Дашборде является суммой уникальных рассчитанных потенциальных штрафов и не допускает двойного учёта одного состава за один нормативный объект и период.

### Проверка

Для состава со ставкой за единицу сумма соответствует ставке и количеству единиц. Для накопительного состава несколько связанных инцидентов формируют один расчёт штрафа за нормативный объект и период; при переходе на следующий порог сумма пересчитывается, но не умножается на количество связанных инцидентов.

## REQ-DEC-031. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-031
**Применимость:** MVP1

При онлайн-проверке Честный знак возвращает исходные данные и признаки о коде маркировки, а не итоговое решение «продавать / не продавать». Кассовое ПО применяет к этим данным действующие правила запрета и формирует собственное решение о допустимости продажи. Инцидент должен раздельно хранить и показывать исходные признаки ответа Честного знака, режим проверки, применённую версию правил, решение кассового ПО и фактическое действие кассы. Формулировки, приписывающие Честному знаку итоговое разрешение или запрет продажи, не используются.

### Проверка
Реализация соответствует решению PM-DEC-031.
## REQ-DEC-007. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-007, PM-DEC-031, PM-DEC-056
**Применимость:** MVP1

Для MVP утверждены следующие бизнес-правила:

- При получении одного отклонения True API создаётся один инцидент с обязательным результатом анализа `RA-01`–`RA-05`.
- Сопоставление выполняется по полному коду маркировки; расхождение времени показывается, но не блокирует сопоставление.
- Если код маркировки отсутствует, результат анализа — `RA-04 — Недостаточно данных`.
- Если тип отклонения неизвестен, результат анализа — `RA-05 — Требуется обновление правил анализа`.
- Если отклонение находится вне розничного выбытия, результат анализа — `RA-03 — Вне поддерживаемых процессов`.
- Подтверждённое нарушение получает результат `RA-01`.
- Найденный корректный сценарий, например возврат перед повторной продажей, получает результат `RA-02`.
- При проверке разрешительного режима сначала используется онлайн-проверка ЧЗ, затем ЛМ ЧЗ только при отсутствии ответа.
- Онлайн Честный знак возвращает исходные признаки, а решение о допустимости продажи формирует кассовое ПО по действующим правилам.
- Продажа, выполненная вопреки сформированному кассовым ПО запрету или с нарушением обязательной последовательности онлайн- и офлайн-проверки, получает результат `RA-01`.
- Инцидент считается критическим только при наличии подтверждённой действующей нормы об автоштрафе на дату кассовой операции.
- Накопительный порог меняет критичность агрегата магазина, но не отдельных инцидентов.
- Конфигурация Set Centrum считается возможным фактором, но не доказательством настроек на момент операции.
- Новая версия правил применяется только к новым инцидентам; ранее созданные инциденты автоматически не пересчитываются.

Каждый результат анализа должен раздельно объяснять исходные данные Честного знака и ЛМ ЧЗ, цепочку операций, решение кассового ПО, фактическое действие кассы, применённое правило и ограничения данных.

### Проверка
Реализация соответствует решениям PM-DEC-007, PM-DEC-031 и PM-DEC-056.

## REQ-DEC-054. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-057
**Применимость:** MVP1

Для ценовых отклонений единое правило применяется к МЦ, МРЦ и ЕМЦ. Если сохранённый результат онлайн ЧЗ или ЛМ ЧЗ содержит применимое ценовое ограничение, но продажа завершена с нарушением, результат анализа — RA-01 и необходимое действие — обращение в поддержку CSI; настройки игнорирования ценовой проверки нет. Если доказано отсутствие результата обоих каналов, необходимо проверить валидацию товарной группы в ЧЗ. Если валидация включена, следует проверить настройку `Разрешить продажу при отсутствии ответа от ЧЗ` и отключить разрешение. Если обе настройки уже корректны, причина не определена достоверно и требуется обращение в CSI. Если исторический результат только отсутствует в доступных данных, применяется RA-04 и запрашиваются логи.

### Проверка
Реализация соответствует решению PM-DEC-057.

## REQ-DEC-060. Решение Product Manager

## REQ-DEC-092. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-107
**Применимость:** MVP1

Для повторных продаж второй очереди применяются три ветки. При повторной продаже у одного продавца менее 30 минут две продажи в SMC означают необходимость проверить блокировку повторной продажи и валидацию категории; одна продажа в SMC при двух продажах в Честном Знаке означает возможную повторную регистрацию чека в ККТ и требует заявки в поддержку. При повторных продажах у разных продавцов необходимо убедиться, что в SMC зафиксирована одна продажа, и далее установить второго продавца через Честный Знак. Если одна из продаж выполнена по агентско-комиссионной схеме, необходимо проверить корректность реквизитов второго юридического лица и переход права собственности.

## REQ-DEC-093. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-108
**Применимость:** MVP1

Инцидент продажи товара, недоступного для реализации, анализируется по полю realizable только при sold=false, поскольку запрет повторной продажи по sold=true имеет более высокий приоритет и относится к правилам повторной продажи. Для табачной продукции после проверки sold учитывается исключение серой зоны: при grayZone=true продажа разрешена даже при realizable=false, применяется RA-02 и настройка игнорирования realizable не проверяется. В остальных случаях значение realizable=false может быть связано с предыдущим выбытием по причине, отличной от розничной продажи, либо с отсутствием ввода товара в оборот. Если кассовое ПО получило realizable=false при неприменимом исключении серой зоны и завершило продажу, проверяется настройка check.excise.ignoreTrueApiMarkRealizable; если игнорирование выключено, требуется обращение в поддержку CSI. Разрешающий сохранённый результат или недостаточная история требуют сверки с Честным Знаком.

Реализация соответствует решению PM-DEC-108.
## REQ-DEC-094. Решение Product Manager

**Область:** businessRules
**Статус:** Подтверждено Product Manager
**Основание:** PM-DEC-109
**Применимость:** MVP1

Для продажи кода групповой упаковки после выбытия сначала проверяется число продаж самой групповой упаковки в SMC. Две продажи анализируются как обычная повторная продажа.
