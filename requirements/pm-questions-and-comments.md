## 1. Замечания к текущему решению

### 1.1. Сценарий пользователя начинается после уже выполненной настройки

Основной путь предполагает, что пользователь открывает Обзор и видит нарушения. При этом данные появляются только после настройки подключения к True API, авторизации УКЭП и первого ответа источника.

Не описан пользовательский путь до появления данных: первое открытие, отсутствие настройки, ожидание первичной загрузки и ошибка загрузки.

Основания: `requirements/05-integrations/data-requirements.md:119-127`, `requirements/07-scenarios/user-journeys.md:14`.

### 1.2. «Нет отдельной настройки» противоречит необходимости настройки True API

Эксплуатационные требования говорят, что отдельной первоначальной настройки у функции нет. Одновременно MVP требует, чтобы администратор настроил подключение к True API и выполнил ручной запуск с УКЭП.

Для пользователя это две разные вещи: установка/включение функции и настройка источника данных. Сейчас они не разделены.

Основания: `requirements/06-system-scenarios/operational-scenarios.md:9`, `requirements/02-system/system-requirements.md:182`.

### 1.3. Не определено ожидаемое поведение после обновления

В требованиях нет продуктового сценария для существующего клиента после появления новой версии Set Mark или SetCentrum. Неясно, должен ли модуль:

- появиться автоматически;
- быть доступен только после включения;
- показывать экран первичной настройки;
- показывать пустой Обзор;
- быть недоступным до выполнения условий;
- сохранять старые данные и настройки;
- требовать повторной настройки.

Основание: `requirements/06-system-scenarios/operational-scenarios.md` содержит общий перечень lifecycle-сценариев, но не описывает ожидаемое пользовательское поведение для данного модуля.

### 1.4. Не определено состояние «данных ещё нет»

Требование отдельно говорит, что отсутствие загруженных данных нельзя показывать как нулевой результат. Однако не описано, какой экран и какое сообщение получает пользователь.

Нужно отличить как минимум:

- подключение не настроено;
- синхронизация ещё не запускалась;
- синхронизация выполняется;
- источник вернул пустой результат;
- данные неполные;
- произошла ошибка;
- данные устарели.

Основание: `requirements/05-integrations/data-requirements.md:123`.

### 1.5. Не разделены доступ к разделу, доступ к данным и готовность данных

Требования одновременно описывают права, лицензию, страну организации, состояние Set Agent, подключение ЭЦП и наличие данных. Но не зафиксирована итоговая таблица поведения для их комбинаций.

Например, неясно, что видит пользователь в следующих случаях:

- есть право, но нет настройки True API;
- есть настройка, но нет лицензии;
- лицензия закончилась, но исторические данные есть;
- нет права просмотра Журнала нарушений;
- страна не `RU`;
- подключение выполнено, но данные ещё не загружены;
- часть ИНН настроена, часть нет.

Основания: `requirements/02-system/roles-and-permissions.md:10`, `requirements/02-system/business-rules.md:21`, `requirements/02-system/system-requirements.md:55-61`.

### 1.6. Не определены границы ответственности администратора

Есть административная привилегия «Настройка подключения к True API», но не описано, кто отвечает за:

- первичное подключение;
- повторную авторизацию;
- запуск синхронизации;
- исправление ошибки подключения;
- контроль свежести данных;
- настройку получателей уведомлений;
- настройку срока хранения.

Основания: `requirements/02-system/roles-and-permissions.md:32, 63-74`, `requirements/05-integrations/integrations.md:109`.

### 1.7. Нет продуктового плана итераций

Есть технический backlog по получению данных True API, но нет согласованной декомпозиции всего MVP: какие пользовательские возможности и состояния появляются в каждой итерации и что считается готовым.

`work-queue.json` не содержит задач.

## 2. Вопросы к Product Manager

### 2.1. Появление модуля у существующего клиента

Что должен увидеть существующий клиент после появления версии с новым модулем: модуль появляется автоматически, появляется выключенным или доступен только после отдельного включения администратором?

**Почему нужно решить:** это определяет ожидаемое поведение после обновления и первый пользовательский экран.

### 2.2. Первичная настройка

Кто должен выполнить первичную настройку подключения True API: администратор системы, любой пользователь с административной привилегией или отдельный ответственный сотрудник? В какой момент настройка считается обязательной для ввода модуля в эксплуатацию?

**Почему нужно решить:** сейчас пользовательский сценарий начинается после настройки, но ответственный и момент настройки не определены.

### 2.3. Первый вход до настройки

Что должен увидеть пользователь с правом доступа при первом открытии модуля, если подключение True API ещё не настроено: Обзор с onboarding-сообщением, отдельный экран настройки, ограниченный Обзор или другой сценарий?

**Почему нужно решить:** текущие требования обещают Обзор, но данные до настройки отсутствуют.

### 2.4. Состояния первичной загрузки

Как должны отображаться состояния «подключение выполнено, но первая синхронизация не запускалась», «синхронизация выполняется», «данные загружены частично», «источник вернул пустой результат» и «синхронизация завершилась ошибкой»?

**Почему нужно решить:** нельзя показывать отсутствие данных как нулевые показатели, но целевые экраны и тексты не определены.

### 2.5. Лицензия и подключение True API

Можно ли настроить и запускать получение данных True API при отсутствии лицензии Set Mark или после её окончания? Что видит обычный пользователь и что видит администратор в этом состоянии?

**Почему нужно решить:** требования разрешают продолжать получение данных при лицензионных ограничениях, но не описывают пользовательское поведение.

### 2.6. Тестовые данные

Какие тестовые данные должны быть предоставлены команде разработки и QA? Должны ли они быть выданы позже, на этапе системной аналитики, или их подготовка должна входить в текущий этап уточнения требований?

Минимально необходимо покрыть: успешную загрузку, пустой ответ, неполные данные, устаревшие данные, ошибки авторизации, повторную доставку, частичный сбой и все результаты `RA-01–RA-05`.

### 2.7. Поведение без тестового True API

Должна ли команда иметь возможность полностью проверить модуль без рабочей УКЭП и обращения к продуктивному True API? Если да, какие демонстрационные и тестовые состояния считаются достаточными для приёмки?

**Почему нужно решить:** рабочий прототип пропущен, а реальный API требует УКЭП и имеет квоты.

### 2.8. Объём MVP по разделам

Какие из разделов обязательны в первой итерации: Обзор, Инциденты, Необходимые действия, Аналитика, Настройки, Журнал нарушений, CSV, PDF и уведомления? Что можно отложить?

**Почему нужно решить:** текущий baseline перечисляет широкий набор возможностей, но не задаёт порядок поставки.

### 2.9. Поведение при обновлении только одного продукта

Какое пользовательское поведение ожидается, если новая функциональность появляется только в Set Mark, а SetCentrum ещё не обновлён, или наоборот? Допускается ли временная недоступность нового модуля до обновления обоих продуктов?

**Почему нужно решить:** Set Mark и SetCentrum поставляются и обновляются независимо, а требования описывают их как единый продуктовый контур.
