## 1. Замечания к текущему решению

### 1.1. Сценарий пользователя начинается после уже выполненной настройки

Основной путь предполагает, что пользователь открывает Обзор и видит нарушения. При этом данные появляются только после настройки подключения к True API, авторизации УКЭП и первого ответа источника.

Не описан пользовательский путь до появления данных: первое открытие, отсутствие настройки, ожидание первичной загрузки и ошибка загрузки.

Основания: `requirements/05-integrations/data-requirements.md:119-127`, `requirements/07-scenarios/user-journeys.md:14`.

### 1.2. «Нет отдельной настройки» противоречит необходимости настройки True API

Эксплуатационные требования говорят, что отдельной первоначальной настройки у функции нет. Одновременно MVP требует, чтобы администратор настроил подключение к True API и выполнил ручной запуск с УКЭП.

Для пользователя это две разные вещи: установка/включение функции и настройка источника данных. Сейчас они не разделены.

Основания: `requirements/06-system-scenarios/operational-scenarios.md:9`, `requirements/02-system/system-requirements.md:182`.

### 1.3. Не определено ожидаемое поведение после обновления

В требованиях нет продуктового сценария для существующего клиента после появления новой версии Set Mark или SetCentrum. Неясно, должен ли модуль:

- быть доступен только после включения и настройки;
- показывать экран первичной настройки;
- быть недоступным до выполнения условий;

Основание: `requirements/06-system-scenarios/operational-scenarios.md` содержит общий перечень lifecycle-сценариев, но не описывает ожидаемое пользовательское поведение для данного модуля.

### 1.4. Не определено состояние «данных ещё нет»

Требование отдельно говорит, что отсутствие загруженных данных нельзя показывать как нулевой результат. Однако не описано, какой экран и какое сообщение получает пользователь.

Нужно отличить как минимум:

- подключение не настроено;
- синхронизация ещё не запускалась;
- синхронизация выполняется;
- источник вернул пустой результат;
- данные неполные;
- произошла ошибка;
- данные устарели.

Основание: `requirements/05-integrations/data-requirements.md:123`.

### 1.5. Не разделены доступ к разделу, доступ к данным и готовность данных

Требования одновременно описывают права, лицензию, страну организации, состояние Set Agent, подключение ЭЦП и наличие данных. Но не зафиксирована итоговая таблица поведения для их комбинаций.

Например, неясно, что видит пользователь в следующих случаях:

- есть право, но нет настройки True API;
- есть настройка, но нет лицензии;
- лицензия закончилась, но исторические данные есть;
- нет права просмотра Журнала нарушений;
- страна не `RU`;
- подключение выполнено, но данные ещё не загружены;
- часть ИНН настроена, часть нет.

Основания: `requirements/02-system/roles-and-permissions.md:10`, `requirements/02-system/business-rules.md:21`, `requirements/02-system/system-requirements.md:55-61`.

### 1.6. Не определены границы ответственности администратора

Есть административная привилегия «Настройка подключения к True API», но не описано, кто отвечает за:

- первичное подключение;
- повторную авторизацию;
- запуск синхронизации;
- исправление ошибки подключения;
- контроль свежести данных;
- настройку получателей уведомлений;
- настройку срока хранения.

Основания: `requirements/02-system/roles-and-permissions.md:32, 63-74`, `requirements/05-integrations/integrations.md:109`.

### 1.7. Нет продуктового плана итераций

Есть технический backlog по получению данных True API, но нет согласованной декомпозиции всего MVP: какие пользовательские возможности и состояния появляются в каждой итерации и что считается готовым.
`work-queue.json` не содержит задач.

### 1.8. Ссылка на требования Петшоп
В документе указана информация об обратной связи "ПетШоп". Этого не должно быть. Нужны требования, а не замечания от клиентов.

### 1.9. Handoff: UI и поведение ручного обновления отклонений True API

В `handoff/` зафиксированы ручной запуск с УКЭП, привилегия «Настройка подключения к True API» и обязанность синхронизации не реже раза в сутки. Не описано продуктовое поведение функции обновления данных для разработчика по handoff:

- где расположена кнопка/действие запуска (Настройки, Обзор, оба экрана, иной вход);
- чем визуально и по шагам отличается «настройка подключения / ЭЦП» от «обновить данные / запустить синхронизацию»;
- какой сценарий выбора ИНН и сертификата УКЭП показывается пользователю;
- что видит пользователь во время SyncRun (прогресс, статусы, возможность уйти со страницы);
- что происходит при повторном запуске чаще раза в сутки или пока предыдущий SyncRun ещё активен;
- как обрабатываются исчерпание квоты True API, частичный успех по товарным группам и ошибка авторизации посреди запуска;
- кто операционно обязан выполнять ежедневный запуск и как система напоминает о просрочке свежести.

Технические ответы частично есть вне handoff (`docs/product-definition/gis-mt-deviations-ingestion-v0.1.md`), но DEVELOPER-START-HERE обещает самодостаточность `handoff/` без внешних материалов.

Основания: `handoff/requirements/02-functional-requirements.md` (`REQ-INT-001`, `REQ-DEC-096`, `REQ-DEC-099`, `REQ-DEC-018`/`097`); `handoff/DEVELOPER-START-HERE.md`.

### 1.10. Не определены канал и технические средства ежедневных уведомлений

Требования фиксируют ежедневное информирование настроенных получателей о критичных нарушениях и переход из уведомления к данным в Set Mark (`REQ-FR-003`). Администратор настраивает получателей; в ограниченном режиме уведомления запрещены. Каналы и периодичность сверх минимального ежедневного сценария явно вне MVP.

При этом не описано:

- каким каналом доставляется уведомление (email, in-app, SMS, мессенджер, существующий канал SetCentrum / Set Mark или иное);
- какими техническими средствами выполняется доставка (SMTP, очередь, платформенный сервис уведомлений);
- время отправки и часовой пояс триггера;
- состав и шаблон сообщения, формат deep-link на инцидент или выборку;
- один дайджест за сутки или отдельное уведомление на каждый критичный инцидент;
- поведение при отсутствии критичных за сутки и при ошибке доставки.

Основания: `requirements/02-system/system-requirements.md` (`REQ-FR-003`), `requirements/01-base/goals-and-scope.md` (`REQ-DEC-003`), `requirements/07-scenarios/business-scenarios.md`, `requirements/07-scenarios/user-journeys.md`.

### 1.11. Не определены ресурсные ограничения и сайзинг при наличии аналитики

Требования запрещают влияние сбоев функции и обработки событий на работу касс и проверку кодов (`REQ-DEC-017`, `REQ-NFR-001`), задают SLA UI: список, карточка и аналитика ≤ 3 с для 95% запросов, и объёмы до 25 000 магазинов / 40 000 касс / 100 000 отклонений в сутки (`REQ-DEC-018`). Одновременно `REQ-NFR-001` и `REQ-NFR-002` оставляют измеримый предел влияния на продажу и критерий успешной нагрузки как `NEEDS_INPUT`.

При этом не описано:

- должны ли системные ресурсы (CPU, память, диск, IOPS) центрального контура и магазинов остаться прежними или допускается их увеличение под новую функциональность;
- как изолировать ресурсоёмкие операции аналитики, агрегатов, CSV и ingestion True API от кассового обмена и продажи;
- бюджеты и лимиты на фоновые задания, concurrent-пользователей аналитики, online-расчёт vs предрасчёт;
- согласованность `REQ-NFR-002` (`NEEDS_INPUT`) с уже утверждёнными объёмами `REQ-DEC-018`.

Инфраструктурный сайзинг в требованиях прямо отложен на инженерную команду и не является входным продуктовым ограничением.

Основания: `requirements/04-quality/quality-requirements.md` (`REQ-DEC-017`, `REQ-NFR-001`, `REQ-NFR-002`), `requirements/05-integrations/data-requirements.md` (`REQ-DEC-018`), `requirements/03-architecture/hardware-requirements.md`, `requirements/03-architecture/technical-constraints.md`.

## 2. Вопросы к Product Manager

### 2.1. Появление модуля у существующего клиента

Что должен увидеть существующий клиент после появления версии с новым модулем: модуль появляется автоматически, появляется выключенным или доступен только после отдельного включения администратором?

**Почему нужно решить:** это определяет ожидаемое поведение после обновления и первый пользовательский экран.

### 2.2. Первичная настройка

Кто должен выполнить первичную настройку подключения True API: администратор системы, любой пользователь с административной привилегией или отдельный ответственный сотрудник? В какой момент настройка считается обязательной для ввода модуля в эксплуатацию?

**Почему нужно решить:** сейчас пользовательский сценарий начинается после настройки, но ответственный и момент настройки не определены.

### 2.3. Первый вход до настройки

Что должен увидеть пользователь с правом доступа при первом открытии модуля, если подключение True API ещё не настроено: Обзор с onboarding-сообщением, отдельный экран настройки, ограниченный Обзор или другой сценарий?

**Почему нужно решить:** текущие требования обещают Обзор, но данные до настройки отсутствуют.

### 2.4. Состояния первичной загрузки

Как должны отображаться состояния «подключение выполнено, но первая синхронизация не запускалась», «синхронизация выполняется», «данные загружены частично», «источник вернул пустой результат» и «синхронизация завершилась ошибкой»?

**Почему нужно решить:** нельзя показывать отсутствие данных как нулевые показатели, но целевые экраны и тексты не определены.

### 2.5. Лицензия и подключение True API

Можно ли настроить и запускать получение данных True API при отсутствии лицензии Set Mark или после её окончания? Что видит обычный пользователь и что видит администратор в этом состоянии?

**Почему нужно решить:** требования разрешают продолжать получение данных при лицензионных ограничениях, но не описывают пользовательское поведение.

### 2.6. Тестовые данные

Какие тестовые данные должны быть предоставлены команде разработки и QA? Должны ли они быть выданы позже, на этапе системной аналитики, или их подготовка должна входить в текущий этап уточнения требований?

Минимально необходимо покрыть: успешную загрузку, пустой ответ, неполные данные, устаревшие данные, ошибки авторизации, повторную доставку, частичный сбой и все результаты `RA-01–RA-05`.

### 2.7. Поведение без тестового True API

Должна ли команда иметь возможность полностью проверить модуль без рабочей УКЭП и обращения к продуктивному True API? Если да, какие демонстрационные и тестовые состояния считаются достаточными для приёмки?

**Почему нужно решить:** рабочий прототип пропущен, а реальный API требует УКЭП и имеет квоты.

### 2.8. Объём MVP по разделам

Какие из разделов обязательны в первой итерации: Обзор, Инциденты, Необходимые действия, Аналитика, Настройки, Журнал нарушений, CSV, PDF и уведомления? Что можно отложить?

**Почему нужно решить:** текущий baseline перечисляет широкий набор возможностей, но не задаёт порядок поставки.

### 2.9. Поведение при обновлении только одного продукта

Какое пользовательское поведение ожидается, если новая функциональность появляется только в Set Mark, а SetCentrum ещё не обновлён, или наоборот? 

**Почему нужно решить:** Set Mark и SetCentrum поставляются и обновляются независимо, а требования описывают их как единый продуктовый контур.

### 2.10. Ручное обновление данных True API в UI

Где в интерфейсе Set Mark / SetCentrum должна находиться кнопка (или эквивалентное действие) ручного обновления отклонений True API? Что должен увидеть пользователь при нажатии: выбор ИНН, выбор УКЭП, подтверждение, прогресс SyncRun?

Что должно происходить, если пользователь запускает обновление чаще одного раза в сутки или повторно, пока предыдущая синхронизация ещё не завершена? Нужно ли блокировать повторный запуск, ставить в очередь, показывать квоту True API?

**Почему нужно решить:** без этого handoff не даёт реализовать точку входа и граничные сценарии синхронизации; техническая спека ingestion не входит в обязательное чтение handoff.

### 2.11. Сценарий SetRetail без Set Mark (`REQ-SO-001`)

`REQ-SO-001` и `REQ-FR-007` допускают для RU-клиента SetRetail без Set Mark ограниченный «Обзор» и «Аналитику» после подключения ЭЦП, без установки Set Mark в магазинах. При этом интеграция True API и владение данными отнесены к серверной части Set Mark, а UI — к оболочке SetCentrum.

Нужно уточнить архитектурную и продуктовую границу этого коммерческого сценария:

- где физически живут получение, хранение и показ ограниченных агрегатов, если у клиента нет Set Mark: в backend Set Mark, в SetCentrum / SetRetail 10 или в другом контуре;
- появляется ли пункт меню «Set Mark» у всех RU-клиентов SetRetail / SetCentrum, включая тех, у кого Set Mark не приобретён;
- что именно считается «работой без Set Mark»: отсутствие лицензии, отсутствие установки в магазинах, отсутствие серверного модуля — или всё вместе.

**Почему нужно решить:** без этого неочевидно, нужно ли менять монолит SetRetail / Centrum ради teaser-режима, и как согласовать `REQ-SO-001` с решением, что интеграция True API принадлежит Set Mark.

### 2.12. Канал и состав ежедневных уведомлений

Каким каналом и какими техническими средствами MVP должен доставлять ежедневные уведомления о критичных нарушениях? Что входит в сообщение, в какое время суток оно формируется и ведёт ли ссылка к конкретному инциденту или к отфильтрованной выборке?

Нужен ли один дайджест за сутки или отдельное уведомление на каждый критичный инцидент? Что происходит, если критичных нарушений за сутки нет или доставка завершилась ошибкой?

**Почему нужно решить:** `REQ-FR-003` требует ежедневные уведомления, но без канала, транспорта, шаблона и расписания реализацию и приёмку нельзя однозначно спроектировать.

### 2.13. Ресурсы и изоляция аналитики от касс

Должны ли системные ресурсы центрального контура и магазинов остаться в текущих пределах после появления Мониторинга, или допускается их увеличение? Какой измеримый предел «отсутствия влияния на продажу» считается приемлемым для приёмки?

Как должны быть разделены ресурсоёмкая аналитика / агрегаты и кассовый контур, чтобы SLA аналитики ≤ 3 с при объёмах до 100 000 отклонений в сутки не создавал риска для работы касс?

**Почему нужно решить:** запрет влияния на кассы есть, а ресурсный бюджет и критерий нагрузки для приёмки (`REQ-NFR-001` / `REQ-NFR-002`) не закрыты; при этом аналитика входит в MVP с жёстким UI-SLA.
